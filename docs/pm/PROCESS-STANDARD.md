## 🎯 核心原则

1. **每个工件必须有CHECKER参与** - Requirement/UI/System Design每个环节都要审核
2. **质量第一** - 不追求速度，追求质量
3. **透明管理** - 所有状态在GitHub可见
4. **流程驱动** - 遵循既定流程，不跳过步骤

---

## 🔄 CHECKER全流程参与

### 每个工件必经三个审核阶段

```
┌─────────────────────────────────────────────────────────────────┐
│                     新功能开发流程                               │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1️⃣ REQUIREMENT 需求审核                                        │
│      ├── CHECKER: 需求是否清晰、完整、无歧义                     │
│      ├── CHECKER: 验收标准是否可量化                             │
│      └── CHECKER: 是否符合业务场景                               │
│                                                                 │
│  2️⃣ UI/DESIGN 设计审核                                         │
│      ├── CHECKER: UI设计是否符合用户体验                         │
│      ├── CHECKER: API设计是否合理                                │
│      └── CHECKER: 系统架构是否满足需求                            │
│                                                                 │
│  3️⃣ CODE 代码审核                                              │
│      ├── CHECKER: 代码质量审查                                   │
│      ├── CHECKER: 安全性审查                                     │
│      └── CHECKER: 性能审查                                       │
│                                                                 │
│  4️⃣ DEPLOY 部署验收                                            │
│      └── CHECKER: 功能验证、集成测试                             │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

## 📊 标准工作流程

### 流程A: 新功能开发（完整版）

```
阶段1: 需求阶段
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. PM 创建Issue
2. PM 分配给REQ角色
3. REQ 撰写需求文档 → CHECKER审核需求 ← 【必须！】
   ✅ 通过 → 进入设计阶段
   ❌ 不通过 → 返回REQ整改

阶段2: 设计阶段
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
4. UI/ARCH 撰写设计方案
   - UI设计 (如涉及前端)
   - API设计 (如涉及接口)
   - 系统架构设计
5. CHECKER审核设计 ← 【必须！】
   ✅ 通过 → 进入开发阶段
   ❌ 不通过 → 返回整改

阶段3: 开发阶段
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
6. DEV 开发代码
7. DEV 创建PR
8. CHECKER代码审查 ← 【必须！】
   ✅ 通过 → 进入测试阶段
   ❌ 不通过 → DEV整改 → 重新审查

阶段4: 部署阶段
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
9. DEVOPS 部署到测试环境
10. CHECKER部署验收 ← 【必须！】
    ✅ 通过 → 进入上线阶段
    ❌ 不通过 → DEVOPS修复 → 重新验收

阶段5: 上线阶段
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
11. PM 合并PR到main
12. DEVOPS 部署到生产
13. CHECKER最终验收 ← 【必须！】
14. PM 关闭Issue
```

---

### 流程B: Bug修复

```
1. PM/QA 发现Bug → 创建Issue (label: bug)
2. PM 分配给DEV
3. DEV 修复 → 创建PR
4. CHECKER代码审查 ← 【必须！】
5. DEVOPS 部署测试环境
6. QA 验证Bug修复
7. CHECKER验收 ← 【必须！】
8. PM 合并 → 关闭Issue
```

## 📋 CHECKER审核检查清单

### 1️⃣ Requirement 需求审核

| 检查项 | 标准 | 通过条件 |
|--------|------|---------|
| 需求完整性 | 包含所有业务场景 | 无遗漏 |
| 需求清晰度 | 无歧义、可理解 | 同行评审通过 |
| 验收标准 | 可量化、可测试 | 3条以上验收标准 |
| 优先级 | 与业务目标一致 | PM确认 |
| 依赖关系 | 外部依赖已识别 | 无未识别依赖 |

**CHECKER输出**: 
```
## Requirement审核结果
✅ 通过 / ❌ 不通过
问题: [...]
整改: [...]
```

---

### 2️⃣ UI/DESIGN 设计审核

#### UI设计检查
| 检查项 | 标准 |
|--------|------|
| 用户体验 | 操作步骤 ≤ 5步 |
| 响应式 | 移动端适配 |
| 一致性 | 风格统一 |
| 可访问性 | 符合WCAG标准 |

#### API设计检查
| 检查项 | 标准 |
|--------|------|
| RESTful | 符合规范 |
| 命名 | 清晰有意义 |
| 响应格式 | 统一 `{ success, data, error }` |
| 错误码 | 完整、有文档 |

#### 系统架构检查
| 检查项 | 标准 |
|--------|------|
| 扩展性 | 支持水平扩展 |
| 安全性 | 符合安全规范 |
| 性能 | 满足SLA |
| 可维护性 | 模块化设计 |

**CHECKER输出**: 
```
## Design审核结果
✅ 通过 / ❌ 不通过
问题: [...]
整改: [...]
```

---

### 3️⃣ CODE 代码审核

| 维度 | 评分项 | 权重 |
|------|--------|------|
| 代码质量 | 风格、命名、结构 | 20% |
| API设计 | RESTful、格式 | 20% |
| 安全性 | 注入、权限、敏感数据 | 25% |
| 性能 | 查询、缓存、索引 | 20% |
| 测试 | 覆盖率、边界测试 | 15% |

**总分**: ≥ 40/50 → ✅ 通过

---

### 4️⃣ DEPLOY 部署验收

| 检查项 | 方法 |
|--------|------|
| 构建 | `docker compose build` 成功 |
| 容器 | 所有容器健康 |
| API | `/api/health` 返回200 |
| 功能 | 核心功能可用 |
| 集成 | 前端访问后端正常 |

## 🚨 违规处理

| 违规 | 处理 |
|------|------|
| 跳过CHECKER审核 | 必须补审 |
| CHECKER未认真审核 | 重新审核 |
| PM跳过流程 | 用户报告，整改 |
| 整改不通过继续 | PM介入 |

## 📊 Issue标签规范

### 角色标签
- `req` - 需求分析
- `dev-backend` - 后端开发
- `dev-frontend` - 前端开发
- `ui` - UI设计
- `arch` - 架构设计
- `ops` - 运维任务
- `qa` - 测试任务
- `checker` - 代码审查

### 状态标签
- `in-progress` - 进行中
- `ready-for-review` - 待审核
- `ready-for-checker` - 待CHECKER审核
- `blocked` - 阻塞
- `done` - 已完成

## 🎯 CHECKER职责

CHECKER是质量守门员，必须在每个工件/功能的每个阶段进行审核：

| 阶段 | CHECKER任务 | 必须审核 |
|------|-----------|---------|
| **1. Requirement** | 需求审核 | ✅ 必做 |
| **2. Design** | 设计审核 | ✅ 必做 |
| **3. Code** | 代码审核 | ✅ 必做 |
| **4. Deploy** | 部署验收 | ✅ 必做 |

---

## 1️⃣ Requirement 需求审核

### 审核时机
- REQ角色完成需求文档后
- 开发前必须审核

### 审核维度

#### 1.1 需求完整性
```
检查:
- [ ] 功能需求是否覆盖所有用户场景
- [ ] 非功能需求（性能、安全、可维护性）
- [ ] 边界条件是否考虑
- [ ] 异常流程是否覆盖
```

#### 1.2 需求清晰度
```
检查:
- [ ] 描述无歧义
- [ ] 术语一致
- [ ] 可被理解
```

#### 1.3 验收标准
```
检查:
- [ ] 验收标准可量化
- [ ] 验收标准可测试
- [ ] 至少3条核心验收标准
```

#### 1.4 业务价值
```
检查:
- [ ] 符合用户实际场景
- [ ] 优先级合理
- [ ] 无过度设计
```

### 评分标准

| 维度 | 权重 | 得分 |
|------|------|------|
| 完整性 | 30% | 0-10 |
| 清晰度 | 30% | 0-10 |
| 验收标准 | 25% | 0-10 |
| 业务价值 | 15% | 0-10 |

**总分**: ≥ 70% → ✅ 通过

### 审核输出格式
```
## CHECKER需求审核报告

### 审核对象
Issue: #XX
需求文档: [链接]

### 评分
| 维度 | 得分 |
|------|------|
| 完整性 | X/10 |
| 清晰度 | X/10 |
| 验收标准 | X/10 |
| 业务价值 | X/10 |
| **总分** | XX% |

### 发现问题
| # | 问题 | 严重程度 | 建议 |
|---|------|---------|------|
| 1 | ... | 高/中/低 | ... |

### 结论
✅ 通过 / ❌ 不通过

### 整改要求（如不通过）
[具体整改项]
```

## 2️⃣ Design 设计审核

### 审核时机
- UI/ARCH完成设计文档后
- 开发前必须审核

### 审核维度

#### 2.1 UI设计审核

| 检查项 | 标准 |
|--------|------|
| 用户体验 | 操作步骤 ≤ 5步完成核心功能 |
| 一致性 | 风格、交互、术语一致 |
| 响应式 | 移动端适配 (320px-1920px) |
| 可访问性 | 颜色对比度、字体大小 |

**UI设计评分**:
```
易用性: X/10
一致性: X/10
响应式: X/10
可访问性: X/10
```

#### 2.2 API设计审核

| 检查项 | 标准 |
|--------|------|
| RESTful | 符合HTTP方法语义 |
| 命名 | 清晰、一致、有意义 |
| 响应格式 | 统一 `{ success, data, error }` |
| 错误码 | 完整、有文档、可追溯 |

**API设计评分**:
```
RESTful规范: X/10
命名清晰: X/10
响应格式: X/10
```

#### 2.3 系统架构审核

| 检查项 | 标准 |
|--------|------|
| 模块化 | 高内聚、低耦合 |
| 扩展性 | 支持水平扩展 |
| 安全性 | 符合安全规范 |
| 性能 | 满足响应时间SLA |

**架构设计评分**:
```
模块化: X/10
扩展性: X/10
安全性: X/10
性能: X/10
```

### 评分标准

| 设计类型 | 权重 |
|----------|------|
| UI设计 | 40% |
| API设计 | 35% |
| 架构设计 | 25% |

**总分**: ≥ 40/50 → ✅ 通过

## 3️⃣ CODE 代码审核

### 审核时机
- DEV创建PR后
- 合并前必须审核

### 审核维度

| 维度 | 权重 | 检查项 |
|------|------|--------|
| 代码质量 | 20% | 风格、命名、结构、注释 |
| API设计 | 20% | RESTful、格式、文档 |
| 安全性 | 25% | 注入、权限、敏感数据、日志 |
| 性能 | 20% | 查询、缓存、索引 |
| 测试 | 15% | 覆盖率、边界测试 |

### 代码质量检查清单

```
代码风格:
- [ ] 符合项目代码规范
- [ ] 命名有意义
- [ ] 函数长度 ≤ 50行
- [ ] 无重复代码 (DRY)

错误处理:
- [ ] 所有异常被捕获
- [ ] 有fallback机制
- [ ] 错误信息友好

代码安全:
- [ ] 无硬编码密码/密钥
- [ ] 无SQL注入风险
- [ ] 输入验证完整
- [ ] 输出脱敏
```

### 评分标准

| 分数 | 等级 | 说明 |
|------|------|------|
| 45-50 | A | 优秀，可合并 |
| 35-44 | B | 良好，小问题可合并 |
| 25-34 | C | 一般，需修复后合并 |
| <25 | D | 差，拒绝合并 |

## 4️⃣ DEPLOY 部署验收

### 审核时机
- DEVOPS完成部署后
- 功能可用前必须验收

### 审核检查清单

#### 4.1 构建验证
```
- [ ] docker compose build 成功
- [ ] 无警告
- [ ] 镜像大小 > 100MB
```

#### 4.2 容器验证
```
- [ ] 所有容器 running
- [ ] 无 restart loop
- [ ] 健康检查通过
```

#### 4.3 API验证
```
- [ ] GET /api/health 返回 200
- [ ] 响应时间 < 500ms
```

#### 4.4 功能验证
```
- [ ] 核心功能可用
- [ ] UI页面是真实应用（非placeholder）
- [ ] 数据正确保存/读取
```

#### 4.5 集成验证
```
- [ ] 前端访问后端正常
- [ ] 无 CORS 错误
- [ ] 无 404 资源
```

### 审核输出格式
```
## CHECKER部署验收报告

### 部署信息
环境: test/staging/production
Commit: xxx
部署时间: xxxx

### 构建验证
✅ / ❌

### 容器验证
✅ / ❌

### API验证
✅ / ❌

### 功能验证
✅ / ❌

### 集成验证
✅ / ❌

### 结论
✅ 通过 / ❌ 不通过

### 问题（如不通过）
[问题列表]
```

## ⚠️ CHECKER注意事项

1. **独立判断** - 不受其他角色影响

4. **及时反馈** - 审核结果24小时内给出

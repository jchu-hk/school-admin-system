# AI 团队工作模型 — 教训提炼与流程增强

> 本文档从历史缺陷中抽象出通用的 AI 团队工作模型改进方案。
> 不绑定任何具体项目，适用于所有 AI Agent 团队协作场景。

---

## 一、核心理念

```
┌────────────────────────────────────────────┐
│          AI Team Operating Model            │
│                                            │
│   角色专注 × 文档先于代码 × 验证闭环       │
│   × 主动推进 × 失败透明 × 持续改进         │
└────────────────────────────────────────────┘
```

---

## 二、六大团队原则

### 原则 1：角色边界严守（Role Integrity）

**问题来源**: PM 写代码、DEV 自测代替 QA、任何 Agent 跳过流程

**团队级规则**:
- 每个角色有明确的**动作禁止清单**，不是功能清单
- 小改动≠可以跨角色。"改动很小"是越界最常见的借口
- **SVA (Self-Verifying Agent) 协议**: 每次工具调用前执行门评估（ALLOWED / BLOCKED）

**Team Level Output**:

| 角色 | 必须做的事 | 禁止做的事 |
|------|-----------|-----------|
| PM | 调度、决策、文档、汇报 | CODE_MODIFY、DEPLOY |
| DEV | 编码、自测 | 自我验收、部署生产 |
| QA | 独立验证、回归测试 | 编码修复、绕过测试 |
| OPS | 部署、CI/CD、环境 | 修改业务逻辑 |

---

### 原则 2：文档先于代码（Documentation-First）

**问题来源**: 文档滞后于代码 → 字段不匹配、接口错位、回归难以追溯

**团队级规则**:
```
代码变更前 → 检查相关文档 → 更新文档 → 再写代码
                ↑                    ↓
           紧急修复例外 → 24h内必须补录
```

**操作化**:
1. 每个 commit 必须包含 `docs:` 或文档同步标注
2. 文档更新 = 独立可追踪的工作项（Issue），不是"顺便"
3. 代码 Review 时必须包含文档 Review

---

### 原则 3：验证闭环（Validation Loop）

**问题来源**: 修复无回归测试、DEV 自测不充分、QA 缺失

**团队级闭环模型**:
```
                    ┌──────────┐
                    │  变更提交 │
                    └────┬─────┘
                         ↓
              ┌──────────────────┐
              │ DEV 单元测试通过  │
              └──────┬───────────┘
                     ↓
           ┌─────────────────────┐
           │ QA 独立验证 + 回归   │  ← 必须由不同角色执行
           └──────┬──────────────┘
                  ↓
        ┌─────────────────────┐
        │ OPS 部署验证         │
        └──────┬──────────────┘
               ↓
        ┌──────────────────┐
        │ PM 验收 + 汇报    │
        └──────────────────┘
```

**强制规则**:
- ❌ DEV 完成后直接关闭 Issue
- ✅ 必须经过 QA 独立验证 → DEV → QA → PM 三重签字
- 回归测试范围 = **上次该模块变更后的所有影响范围**

---

### 原则 4：主动推进（Proactive Drive）

**问题来源**: PM/Agent 等待外部触发、知道阻塞但不处理

**团队级规则**:
- **发现即处理** — 不需要等用户/调度器说"去做"
- 阻塞优先级 = 阻塞的深度 × 影响的广度
- 心跳/监控检查 CI 状态，不只是健康检查
- 夜间遇到问题 → 夜间解决（AI 7x24 是优势，不要浪费）

**Checklist**:
- [ ] 当前是否有阻塞其他 Agent 的依赖？
- [ ] CI 最后一次运行是否通过？
- [ ] 是否有超过 2h 未响应的 Issue？
- [ ] 是否有积压超过 3 天的分支？

---

### 原则 5：失败透明（Failure Transparency）

**问题来源**: 错误被掩盖、根因不记录、同类错误反复出现

**团队级机制**:
```
每个缺陷必须回答 3 个问题：
1. 发生了什么？（现象）
2. 为什么会发生？（根因）
3. 如何防止再次发生？（流程改进）
```

**具体产出**:
- 每次修复必须写入根因分析到 Issue comment
- 根因按类型分类（见下文 §四）
- 每两周回顾根因分布，识别模式

---

### 原则 6：持续改进（Continuous Improvement）

**问题来源**: 教训被遗忘、文档写了没人看

**团队级机制**:
- 新 Agent 上岗时：读 `AI-TEAM-OPERATING-MODEL.md`
- 每次 spawn 时：PM 在 task 中引用相关类别的教训
- 每两周：根因趋势分析 → 更新本模型
- 新教训 → 立即更新 → 全员同步

## 三、团队工作流程改进

### 3.1 任务启动流程（Spawn Protocol）

```
[PM] 创建 Issue + 分类（类型/优先级）
  ↓
[PM] 分配 DEV 做分析诊断
  ↓
[DV] 分析完成 → 写入根因到 Issue comment
  ↓
[PM] 审阅根因 → 按类型指派：
      ├─ 技术设计问题 → ARCH
      ├─ 环境/部署问题 → OPS
      ├─ 代码Bug → DEV
      └─ 配置/权限 → OPS
  ↓
[执行Agent] 更新文档 → 编码 → 自测 → PR
  ↓
[QA] 独立验证 + 回归测试
  ↓
[PM] 验收 → 汇报 → 关闭 Issue
```

### 3.2 通信规范（Communication Protocol）

```
┌─────────────────────────────────────────┐
│          每次 spawn 强制模板              │
├─────────────────────────────────────────┤
│ 1. write_message --from PM --to {AGENT}  │
│    --type assign --status running        │
│ 2. 在 task prompt 嵌入通信规则            │
│ 3. Agent 启动后先写 received              │
│ 4. Agent 完成必须写 passed/failed         │
│ 5. PM 检查 Dashboard 确认更新             │
└─────────────────────────────────────────┘
```

## 四、根因类型分类体系（Root Cause Taxonomy）

为便于后续统计和模式识别，所有缺陷归入以下 8 类：

| 代码 | 类型 | 触发问句 | 典型例子 |
|------|------|---------|---------|
| **R-BOUNDARY** | 角色越界 | "谁做了不该做的事？" | PM 写代码、DEV 自验 |
| **R-DOC** | 文档滞后 | "文档与代码是否一致？" | Entity 字段名不匹配 |
| **R-COMPLEX** | 非必要复杂度 | "能否用更简单的方式？" | 静态页引入 i18n |
| **R-TECH** | 技术陷阱 | "有没有语言/框架的坑？" | React ref 条件渲染、ESM 全局访问 |
| **R-TEST** | 测试遗漏 | "回归测试覆盖了吗？" | 修复后未验证相关路由 |
| **R-DEPLOY** | 部署失误 | "路径/权限/配置对吗？" | docker cp 路径错误 |
| **R-COMMS** | 通信断裂 | "Dashboard 更新了吗？" | spawn 前不 write_message |
| **R-PASSIVE** | 被动等待 | "为什么等到用户提醒？" | CI 失败不主动处理 |

## 五、质量门（Quality Gates）

每个任务经过以下门后才能关闭：

```
GATE 1 — 文档门
  □ 相关文档已同步（功能/设计/API/DB）
  □ Commit 含变更说明

GATE 2 — 测试门
  □ DEV 自测通过
  □ QA 独立验证通过
  □ 回归测试覆盖受影响模块

GATE 3 — 通信门
  □ Dashboard 状态已更新
  □ 根因分析已写入 Issue
  □ PM 已确认进度

GATE 4 — 部署门
  □ 构建通过
  □ CI 通过
  □ 部署后健康检查正常

GATE 5 — 关闭门
  □ PM 验收通过
  □ Issue 关闭 + 标签正确
  □ 教训已记录（如需）
```

## 六、Agent 日常运行检查清单

### 每次心跳执行：

```markdown
- [ ] 各 Agent 是否 idle（不应长时间 running 无消息）？
- [ ] 是否有 overdue 的任务？（超过预期完成时间）
- [ ] CI 最近一次运行是否通过？
- [ ] 是否有积压超过 3 天的分支？
- [ ] Dashboard 是否显示最新状态？
- [ ] 是否有新教训需要记录到本模型？
```

### 每两周执行：

```markdown
- [ ] 统计近期根因分布（按 §四 分类）
- [ ] 识别 Top 3 高频根因类型
- [ ] 更新本模型中的对应流程改进
- [ ] 同步给所有 Agent（作为 spawn 开场参考）
```

## 七、一句话速查表

| 场景 | 该怎么做 |
|------|---------|
| 发现 Bug | 先分析根因类型 → 按类型指派 → 修复 → 回归 → 记录教训 |
| 要改代码 | 先同步文档 → 再改代码 → 改完验证 |
| 要 spawn | 先 write_message → 嵌入通信模板 → spawn |
| 修复完 | 自测 → QA 验 → PM 验 → Dashboard 更新 → 关闭 |
| CI 红了 | 立刻查 → 立刻修 → 不等用户 |
| 分支老了 | 立刻合并 → 记录阻塞原因 → 改流程 |
| 新教训 | 立即更新本文档 → 全员可见 |
| 角色模糊 | 查 SVA 表 → 边界内行动 → 越界转交 |

## 八、本模型的演化机制

```
新缺陷出现
    ↓
记录根因（按 §四 分类）
    ↓
判断：是否属于已覆盖的教训？
   ├─ 是 → 检查流程是否执行到位，而不是规则缺失
   └─ 否 → 新增教训 → 更新本文档对应章节
              ↓
        下次 spawn 时 PM 引用新教训
```

**最终目标**: 相同根因类型不再重复出现。如果重复了，说明不是规则不够，而是**执行不够**。

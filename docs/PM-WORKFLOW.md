# AI团队角色定义与PM工作流程 (AI Team Roles & PM Workflow)

**版本**: v3.0
**创建日期**: 2026-06-21
**最后更新**: 2026-06-21

---

## AI团队角色定义

| 角色 | 职责 |
|------|------|
| **PM** | 项目管理、任务分配、进度跟踪、验收 |
| **REQ** | 需求分析、功能设计、功能规格输出 |
| **ARCH** | 系统架构、技术设计 |
| **UI** | 界面设计、交互设计 |
| **DEV** | 代码开发、功能实现 |
| **CHECKER** | 全面质量保证（检查所有交付物） |
| **DEVOPS** | 部署、CI/CD、环境维护 |
| **QA** | 测试、验证、数据准备 |
| **OPS** | 上线、支持、维护 |

---

## 1. PM (Project Manager)

### 核心职责
- 接收人类需求
- 调用 REQ 分析系统需求
- 制定工作计划
- 分配任务给对应角色
- 跟踪进度
- 验收交付物

### 不做的事
- ❌ 亲自编写代码
- ❌ 亲自设计UI
- ❌ 亲自设计架构
- ❌ 亲自执行测试
- ❌ 亲自运维部署

---

## 2. REQ (Requirements Engineer)

**职责**: 负责系统需求分析、功能设计和功能规格说明输出

**任务**:
- 需求收集和分析
- 功能设计
- 编写规格文档
- 需求评审

**输出**: 功能规格文档（Functional Specification）

**报告模板**:
```markdown
## 📋 REQ 完成报告
**需求文档**: [文档名称]
**输出文档**: ✅ [文档1]
**下一步**: 请PM调用 CHECKER 检查质量
```

---

## 3. ARCH (System Architect)

**职责**: 负责系统架构设计和系统技术设计

**任务**:
- 系统分析和架构设计
- 技术选型
- 接口设计
- 数据库设计
- 安全设计
- 性能设计

**输出**: 架构文档、技术设计文档、API规范、ER图

**报告模板**:
```markdown
## 🏗️ ARCH 完成报告
**架构文档**: [文档名称]
**输出**: ✅ [架构、技术、API、数据库设计]
**下一步**: 请PM调用 CHECKER 检查质量
```

---

**职责**: 根据功能规格进行用户界面设计

**任务**:
- 用户研究
- 信息架构
- 界面设计
- 交互设计
- 原型制作
- 设计规范

**输出**: 原型文档、设计规格、设计稿

**报告模板**:
```markdown
## 🎨 UI 完成报告
**设计文档**: [文档名称]
**输出**: ✅ [原型、设计规格]
**下一步**: 请PM调用 CHECKER 检查质量
```

## 5. DEV (Developer)

**职责**: 代码开发和功能实现

**任务**:
- 代码开发
- 单元测试
- 代码审查


## 6. CHECKER (Quality Assurance Inspector)

**职责**: 全面质量保证，独立检查所有角色的输出交付物

### 6.1 检查范围

| 角色 | 检查内容 | 标准 |
|------|----------|------|
| **REQ** | 功能规格文档 | 需求清晰、完整、可测试；符合IEEE 830标准 |
| **ARCH** | 架构设计、技术设计 | 架构合理、技术选型恰当、符合SOLID/DDD |
| **UI** | 设计稿、设计规范 | 用户体验最佳实践、响应式设计 |
| **DEV** | 代码、PR | 代码规范、安全性、性能、最佳实践 |
| **DEVOPS** | 部署配置、CI/CD | 符合DevOps最佳实践 |
| **QA** | 测试用例、测试报告 | 测试用例覆盖功能规格、测试报告完整 |

### 6.2 具体检查项

**REQ检查**:
- [ ] 需求清晰完整
- [ ] 包含验收标准（Acceptance Criteria）
- [ ] 技术可行性确认
- [ ] 符合行业标准（IEEE 830）

**ARCH检查**:
- [ ] 架构清晰合理
- [ ] 技术选型恰当
- [ ] 接口定义完整
- [ ] 数据模型正确
- [ ] 安全设计充分
- [ ] 性能考虑周全

**UI检查**:
- [ ] 包含所有功能页面
- [ ] 交互流程清晰
- [ ] 响应式设计
- [ ] 设计规范完整
- [ ] 符合用户体验最佳实践

**DEV检查**:
- [ ] 代码质量符合规范
- [ ] 无安全漏洞
- [ ] 性能优化合理
- [ ] 遵循最佳实践
- [ ] 文档完整

**QA检查**:
- [ ] 测试用例覆盖功能规格
- [ ] 测试用例设计合理
- [ ] 测试报告完整清晰
- [ ] Bug记录准确

### 6.3 报告模板

```markdown
## 🔍 CHECKER 质量检查报告

**检查对象**: [角色] - [交付物名称]
**CHECKER Agent**: @CHECKER
**检查时间**: [时间]

**检查结果**:
- ✅ 需求清晰度: [评价]
- ✅ 完整性: [评价]
- ✅ 规范符合度: [评价]
- ❌ [问题]: [描述和建议]

**结论**:
- [ ] 通过 - 可继续下一环节
- [ ] 需修改 - 打回原角色修改

**下一步**: [通知PM继续/打回原角色]
```

## 7. DEVOPS (Operations Engineer - Deployment)

**职责**: 部署和CI/CD

**任务**:
- 部署配置
- CI/CD流水线
- 环境维护

**输出**: 部署文档、CI/CD配置

**报告模板**:
```markdown
## 🚀 DEVOPS 完成报告
**部署任务**: [任务名称]
**输出**: ✅ [部署文档、CI/CD配置]
**下一步**: 请PM调用 CHECKER 检查质量
```

---

## 8. QA (Quality Assurance - Tester)

**职责**: 测试和质量验证

**任务**:
- 测试计划
- 测试用例设计（**必须对照功能规格**）
- 功能测试
- 集成测试
- Bug记录
- 数据准备

**输出**: 测试计划、测试用例、测试报告

**报告模板**:
```markdown
## ✅ QA 完成报告
**测试计划**: [计划名称]
**测试用例**: [数量] 个
**下一步**: 请PM调用 CHECKER 检查测试用例设计
```

```markdown
## ✅ QA 验收报告
**任务**: [任务名称]
**Issue**: [#XX](链接)
**测试结果**: ✅ [测试项]
**结论**: [通过/不通过]
**下一步**: [通知PM/打回DEV]
```

---

## 9. OPS (Operations Engineer - Go-live & Support)

**职责**: 系统上线、支持和维护

**任务**:
- 环境搭建
- 上线部署
- 监控告警
- 故障处理
- 日常维护
- 安全运维

**输出**: 部署指南、监控指南、运维文档

## 完整工作流程

### 新功能开发流程

```
人类需求
  ↓
PM 接收
  ↓
PM 调用 REQ
  ↓
REQ 输出需求文档
  ↓
PM 调用 CHECKER（检查需求文档质量）
  ↓
CHECKER 通过?
  ├─ 否 → 打回 REQ 修改
  └─ 是 → 继续
  ↓
PM 调用 ARCH
  ↓
ARCH 输出架构文档
  ↓
PM 调用 CHECKER（检查架构文档质量）
  ↓
CHECKER 通过?
  ├─ 否 → 打回 ARCH 修改
  └─ 是 → 继续
  ↓
PM 调用 UI
  ↓
UI 输出设计稿
  ↓
PM 调用 CHECKER（检查设计稿质量）
  ↓
CHECKER 通过?
  ├─ 否 → 打回 UI 修改
  └─ 是 → 继续
  ↓
PM 分配给 DEV
  ↓
DEV 开发
  ↓
PM 调用 CHECKER（检查代码质量）
  ↓
CHECKER 通过?
  ├─ 否 → 打回 DEV 修改
  └─ 是 → 继续
  ↓
PM 合并到 main
  ↓
PM 调用 DEVOPS 部署
  ↓
DEVOPS 输出部署文档
  ↓
PM 调用 CHECKER（检查部署配置质量）
  ↓
CHECKER 通过?
  ├─ 否 → 打回 DEVOPS 修改
  └─ 是 → 继续
  ↓
PM 调用 QA 设计测试用例
  ↓
QA 输出测试用例
  ↓
PM 调用 CHECKER（检查测试用例是否覆盖功能规格）
  ↓
CHECKER 通过?
  ├─ 否 → 打回 QA 修改
  └─ 是 → 继续
  ↓
QA 执行测试
  ↓
QA 输出测试报告
  ↓
PM 调用 CHECKER（检查测试报告质量）
  ↓
CHECKER 通过?
  ├─ 否 → 打回 QA 补充
  └─ 是 → 继续
  ↓
QA 验收通过?
  ├─ 否 → 打回 DEV 修复
  └─ 是 → 继续
  ↓
PM 调用 OPS 上线
  ↓
OPS 上线
  ↓
PM 关闭 Issue
```

### Bug修复流程

```
Bug报告
  ↓
PM 记录到 Issue
  ↓
PM 分配给 DEV
  ↓
DEV 修复
  ↓
PM 调用 CHECKER（检查代码质量）
  ↓
CHECKER 通过?
  ├─ 否 → 打回 DEV
  └─ 是 → 继续
  ↓
PM 合并
  ↓
PM 调用 DEVOPS 部署
  ↓
PM 调用 CHECKER（检查部署配置）
  ↓
PM 调用 QA 验证
  ↓
QA 输出测试报告
  ↓
PM 调用 CHECKER（检查测试报告）
  ↓
QA 通过
  ↓
PM 调用 OPS 上线
  ↓
PM 关闭 Issue
```

## PM调用角色的时机

| 时机 | 调用角色 |
|------|----------|
| 收到新需求 | REQ |
| REQ完成后 | CHECKER（检查需求文档） |
| 需求检查通过 | ARCH |
| ARCH完成后 | CHECKER（检查架构文档） |
| 架构检查通过 | UI |
| UI完成后 | CHECKER（检查设计稿） |
| 设计检查通过 | DEV |
| DEV完成后 | CHECKER（检查代码） |
| 代码检查通过 | DEVOPS |
| DEVOPS完成后 | CHECKER（检查部署配置） |
| 部署检查通过 | QA（设计测试用例） |
| 测试用例完成后 | CHECKER（检查测试用例） |
| 测试用例检查通过 | QA（执行测试） |
| 测试完成后 | CHECKER（检查测试报告） |
| 测试报告检查通过 | 判断QA是否通过 |
| QA通过 | OPS |
| 运维问题 | OPS |

---

## 关键质量保证点

1. **每个交付物必须经过CHECKER检查**
2. **QA测试用例必须对照功能规格**
3. **CHECKER可以打回任何不合格的交付物**
4. **只有CHECKER通过后才能进入下一环节**

## 2. 设计背景与目标

### 2.1 现状问题

- 传统校园考勤依赖实体 IC 卡刷卡或人工签字，存在卡片丢失、代刷、统计滞后等问题
- 2000+ 学生的考勤数据无法实时汇总，班主任需手动统计迟到/缺勤
- 早高峰期校门口闸机通行速度慢（刷卡 → 识别 → 开门平均 5-10 秒/人）

### 2.2 核心目标

1. **通行效率**：将入校通行时间压缩至 **2-3 秒/人**（展示二维码 + 扫码）
2. **数据实时性**：考勤数据实时更新，班主任可在系统即时查看当日到校情况
3. **成本降低**：替换物理卡片成本（补卡、发卡、消磁等维护工作）
4. **安全防伪**：防代签、防伪造、防重复签到
5. **高可用性**：支持离线场景（校园网络不稳定时仍可正常运作）

### F-ATTQR-001: 动态 QR Code 生成

**标识：** F-ATTQR-001 | P1

#### 目的

为学生生成短期有效的动态 QR Code，用于入口签到考勤。

#### 输入

| 字段 | 类型 | 必填 | 来源 | 说明 |
|------|------|------|------|------|
| student_id | UUID | 是 | 系统自动 | 学生档案ID |
| device_id | String | 否 | 客户端上报 | 学生端设备标识（可选，用于安全风控）|
| session_token | String | 是 | 系统生成 | OAuth/token 会话标识 |

#### QR 码编码规则

| 字段 | 格式 | 长度 | 说明 |
|------|------|------|------|
| 协议标识 | `SCHQR` | 5字节 | 固定前缀，标识校园QR码 |
| 版本号 | `01` | 2字节 | QR码协议版本 |
| 时间戳 | `YYYYMMDDHHMMSS` | 14字节 | 生成时间（UTC+8） |
| 学生标识 | `student_id` UUID | 36字节 | 学生唯一标识 |
| 随机数 | 16位十六进制 | 16字节 | 防重放攻击随机因子 |
| 密钥签名 | SHA256 完整哈希 | 32字节 | 服务端私钥签名，防篡改 |
| **总计** | | **≤ 105字节** | 编码为 Base64 后约 140 字符 |

#### 编码输出格式

```
SCHQR|01|YYYYMMDDHHMMSS|UUID|RANDOM|SIGNATURE
```

最终编码为 QR Code 时使用 **Byte mode**，纠错等级 **M (15%)**，版本自动适配以适应约 140 字符内容。

#### 业务规则

1. QR Code **有效期：30 秒**（从生成时间算起，过期后自动失效）
2. 每生成新码时上次生成的码自动失效（**一人一码，一次有效**）
3. 服务端校验：解析 QR 内容 → 验证签名 → 检查有效期 → 检查是否已被使用
4. 签名密钥**每日轮换**，由服务端密钥管理系统管理

#### 输出

```json
{
  "qr_code_content": "SCHQR|01|20260714080000|uuid-xxx|a1b2c3d4e5f6g7h8|signature_bytes_base64",
  "qr_code_image_url": "https://attendance-api.school.edu/v1/qr/generate-image?data=...",
  "expires_at": "2026-07-14T08:00:30+08:00",
  "generated_at": "2026-07-14T08:00:00+08:00"
}
```

#### 验收标准 (AC)

| # | Given（前置条件） | When（操作） | Then（预期结果） |
|---|----------------|------------|----------------|
| AC-01 | 学生进入校门，打开签到页面 | 系统调用 QR 生成接口 | 返回有效 QR Code，过期时间 = 生成时间 + 30秒 |
| AC-02 | QR 码生成后超过 30 秒 | 扫码枪扫描旧码 | 服务器返回 410 Gone，提示"二维码已过期" |
| AC-03 | 签名密钥每日轮换 | 生成新 QR 码 | 使用当日最新密钥签名，旧密钥签名的码视为无效 |
| AC-04 | QR 码内容包含 UUID | 攻击者尝试篡改内容 | 签名验证失败，返回 403 禁止访问 |

### F-ATTQR-002: 扫码签到（教职员工/闸机）

**标识：** F-ATTQR-002 | P1

#### 目的

教职员工手持终端或闸机扫码枪扫描学生 QR Code，完成考勤记录。

#### 输入

| 字段 | 类型 | 必填 | 来源 | 说明 |
|------|------|------|------|------|
| qr_raw_content | String | 是 | 扫码设备 | 从 QR Code 解码出的原始字符串 |
| scanner_device_id | String | 是 | 扫码设备 | 扫码终端的设备标识 |
| scanner_location | String | 是 | 扫码设备 | 扫码位置（如：正门/侧门/地下入口） |
| scanned_at | DateTime | 是 | 扫码设备 | 设备本地时间（用于离线校验） |

#### 业务规则

1. **防重复签到（核心安全约束）：** 同一 QR Code 的唯一签名组合只能被扫码一次，第二次返回 **409 Conflict**
2. **时间窗口防刷：** 同学生在 **5 分钟窗口期**内，即使生成新 QR 码也只能记一次签到（防止一分钟多次刷码）
3. **离线容灾：** 当闸机检测到网络中断时，自动进入**离线模式**：扫码记录本地缓存（SQLite 本地数据库或文件存储），网络恢复后批量同步至服务端
4. 教职员工的扫码操作本身也被记录为**操作审计日志**

#### 离线模式数据格式

```json
{
  "cache_id": "UUID",
  "qr_content_hashed": "SHA256",
  "qr_student_id": "uuid",
  "scanner_device_id": "string",
  "scanner_location": "string",
  "scanned_at_local": "2026-07-14T08:01:00+08:00",
  "cached_at": "2026-07-14T08:01:00+08:00",
  "synced": false
}
```

#### 输出（在线模式）

```json
{
  "attendance_id": "uuid",
  "student_id": "uuid",
  "student_name": "王小明",
  "student_class": "1A",
  "check_in_time": "2026-07-14T08:00:15+08:00",
  "location": "正门",
  "scanner_device": "gate-01",
  "status": "on_time",
  "message": "签到成功"
}
```

#### 验收标准 (AC)

| # | Given（前置条件） | When（操作） | Then（预期结果） |
|---|----------------|------------|----------------|
| AC-01 | 学生展示有效 QR Code | 教职员工扫码枪扫描 | 系统记录签到成功，状态 on_time |
| AC-02 | 同一 QR Code 被连续扫码两次 | 第二次扫码请求 | 返回 409 Conflict，提示"该二维码已被使用" |
| AC-03 | 学生在 5 分钟内连续生成并展示新码 | 第二次被扫码 | 返回 429 Too Many Requests，提示"请勿重复签到" |
| AC-04 | 闸机网络断线 | 扫码后在本地缓存 | SQLite 缓存条目 synced=false，本地存储可用空间 > 100MB |
| AC-05 | 闸机网络恢复 | 自动触发批量同步 | 所有 synced=false 的记录上传至服务端，synced 标记为 true |

### F-ATTQR-003: 日报表推送

**标识：** F-ATTQR-003 | P1

#### 目的

每日定时向班主任推送班级考勤日报。

#### 业务规则

1. 每日 **08:30** 自动生成当日截至当前的签到日报
2. 迟到判定标准：**08:00** 之后签到记为迟到（可配置）
3. 缺勤判定：08:30 仍未签到且无提前请假记录的学生记为缺勤
4. 推送渠道：系统通知、飞书/钉钉消息、Web 后台仪表板
5. 日报内容：应到人数、已签到人数、迟到人数、缺勤人数、未签到学生名单

#### 输出

```json
{
  "report_date": "2026-07-14",
  "class": "1A",
  "total_students": 32,
  "checked_in": 28,
  "late": 2,
  "absent": 2,
  "leave_approved": 1,
  "unchecked_students": [
    {"student_id": "uuid", "name": "李四", "status": "absent"},
    {"student_id": "uuid", "name": "张三", "status": "absent"}
  ]
}
```

#### 验收标准 (AC)

| # | Given（前置条件） | When（操作） | Then（预期结果） |
|---|----------------|------------|----------------|
| AC-01 | 每日 08:30 到达 | 系统触发日报生成 | 生成每个班级的签到日报，包含应到/已签/迟到/缺勤统计 |
| AC-02 | 班主任登录系统 | 查看日报仪表板 | 显示当日所带班级的完整签到数据 |
| AC-03 | 推送渠道配置生效 | 日报生成后 | 通过系统通知/飞书/钉钉消息推送给班主任 |

### F-ATTQR-004: 家长考勤查询

**标识：** F-ATTQR-004 | P2

#### 目的

支持多家长绑定同一学生，家长可通过门户查看子女的签到记录。

#### 业务规则

1. 支持**多家长绑定**（通过 `parent_student_links` 关联表）
2. 家长可查看：
   - 当日签到状态
   - 历史签到记录（最近 **30 天**）
   - 迟到/缺勤统计
3. 家长**不可修改**签到记录（仅读权限）
4. 数据隔离：家长只能查看自己关联学生的数据

#### 验收标准 (AC)

| # | Given（前置条件） | When（操作） | Then（预期结果） |
|---|----------------|------------|----------------|
| AC-01 | 家长登录门户 | 访问「考勤记录」页面 | 显示已绑定学生的当日签到状态 |
| AC-02 | 家长查看历史考勤 | 选择时间范围 | 展示最近 30 天的签到记录及迟到/缺勤统计 |
| AC-03 | 家长尝试修改签到记录 | 发送修改请求 | 返回 403 Forbidden，提示"无权操作" |
| AC-04 | 家长未绑定某学生 | 尝试查看该学生的考勤 | 页面不显示该学生信息，API 返回 403 |

## 4. 学生端展示渠道选型

### 4.1 选型对比

| 选型维度 | 原生 App (Native) | 移动 Web (Web Portal / PWA) |
|----------|-----------------|---------------------------|
| **QR 码渲染性能** | ★★★★★ 原生渲染，快速稳定 | ★★★★☆ Web Canvas 渲染，低端机有延迟 |
| **离线能力** | ★★★★★ 本地缓存+离线QR生成 | ★★★☆☆ PWA Service Worker 有限离线 |
| **摄像头调用** | ★★★★★ 原生 API 无缝 | ★★★★☆ WebRTC 调用，需 HTTPS + 用户授权 |
| **自动刷新** | ★★★★★ 后台定时器精确刷新 | ★★★★☆ JavaScript setInterval 受标签页活跃度影响 |
| **部署成本** | ★★☆☆☆ App Store / 应用商店审核 | ★★★★★ 零部署，浏览器访问即用 |
| **更新频率** | ★★☆☆☆ 需发版更新 | ★★★★★ 服务端更新即生效 |
| **设备兼容性** | ★★★★☆ 需 iOS/Android 双端开发 | ★★★★★ 跨平台，无需双端开发 |
| **安全性** | ★★★★★ 沙箱环境+Fingerprint | ★★★★☆ HTTPS + 浏览器安全模型 |
| **开发维护成本** | ★☆☆☆☆ 高（双平台+发版） | ★★★★★ 低（一套代码） |

### 4.2 选型结论：推荐使用 Web Portal（PWA）方案

**选型理由：**

1. **部署零门槛**：学生无需安装 App，打开浏览器即可使用，特别适合 2000+ 学生规模的 K-12 学校（学生手机可能无足够存储空间或家长不允许安装额外 App）
2. **成本优势**：无需 iOS/Android 双端开发团队，单一 Web 代码库降低 70%+ 开发维护成本
3. **QR 码刷新**：通过 Service Worker + Web Workers 实现后台定时刷新，配合高频（2 秒）setInterval 确保 30 秒有效期内的二维码始终可用
4. **离线补偿**：PWA 的 Service Worker 可缓存初始页面，QR 码实时刷新仍需在线（与闸机离线模式互补）
5. **渐进增强**：先以 Web Portal 上线，后续可按需升级为 App（留原生 API 接口）

## 5. 核心约束与安全要求

| 维度 | 约束 |
|------|------|
| **QR 码有效期** | 30 秒（短期有效，过期自动失效） |
| **QR 编码格式** | `SCHQR\|01\|YYYYMMDDHHMMSS\|UUID\|RANDOM\|SIGNATURE` |
| **签名算法** | HMAC-SHA256，密钥每日轮换 |
| **防重放** | 随机数 16 字节 + 一次性使用标记 |
| **防重复** | 同一学生 **5 分钟窗口期**内仅记一次签到 |
| **传输安全** | 全链路 HTTPS，QR 内容仅服务端完整解析 |
| **离线缓存加密** | 闸机本地缓存用 **AES-256** 加密存储 |
| **扫码设备认证** | 每个扫码终端需注册并分配 API Key，未经注册的设备扫码请求被拒绝 |
| **日志审计** | 所有 QR 生成、扫码、同步操作记入 `attendance_audit_log` 表 |

## 1. 需求背景与目标

AI SRE 运维 Agent 应是一个**通用、可部署、可学习、可支持新系统**的运营 Agent，而非仅为单一系统定制。它以自包含可部署单元交付，通过配置驱动与适配器插件模型接入任意新系统，并对每个接入系统进行行为学习与基线建模，实现「接入即用、越用越准」。

**School Admin System（SAS）是 AI SRE 的第一个参考部署实例（reference deployment），而非其唯一目标系统。** 本规格以 SAS（13 个 Docker 容器、PostgreSQL/Redis/文件存储、多个前端入口、多 Agent 运维团队）为例给出首个落地场景（详见附录「参考实例配置」），但所有功能需求均以「系统无关」为原则表述，SAS 的拓扑、端口、路径、组件构成均通过配置/适配器注入，不写死进 AI SRE 本体。

本规格旨在为 AI SRE Agent 定义清晰的职责边界与协作接口，使其成为团队中「全天候值守、先于用户感知问题、先于人工处理简单故障」的运维角色，同时与现有 PM 调度、DEV 修 bug、QA 验证、DEVOPS 部署的流程无缝衔接。

**核心能力定位（三大核心目标）**：
- **可部署（Deployable）**：以自包含单元（容器镜像 + 编排清单 + 一键接入脚本）交付，任意新环境凭配置即可运行。
- **可学习（Can Learn）**：对新系统从冷启动逐步学习基线指标与异常模式，检测阈值与自愈策略随系统行为动态调整。
- **可支持新系统（Support New System）**：接入新系统不改核心代码，只加配置或适配器，即可完成组件发现、建模与纳管。

## 2. 功能边界（Functional Scope）

### 检测边界：可用性/可靠性 而非 功能正确性
> AI SRE 的自动化监控信号（F-SRE-001）全部是**可用性/可靠性类指标**（服务健康、资源、容器/进程、数据库/缓存连接、磁盘、日志 ERROR 簇、Agent 心跳）。它**检测不到「功能正确性」**——即业务逻辑是否正确、返回的结果数据是否正确的这类问题。
>
> - AI SRE 只检测「系统健康运行」层面，不检测「功能是否按预期产出正确结果」。系统健康 ≠ 功能正确：可能存在「健康检查通过、指标正常、但具体功能不工作」的盲区。
> - 仅当功能缺陷**泄露了可观测信号**时，AI SRE 才会「顺带」发现：后端抛异常堆栈 → 日志出现 ERROR 簇；接口 5xx / 错误率异常升高；DB 查询报错等。
> - **静默 bug**（如接口返回 200 但数据错、页面空白但不抛错、逻辑分支走错却不报错）不产生上述信号，AI SRE **无感知**。
> - 这类功能缺陷的兜底来自：**QA 功能测试**（验证业务正确性）+ **F-SRE-014 用户报障接入**（用户在使用中直接反馈功能不工作）。
>
### F-SRE-001 运行状态自主监控
AI SRE 必须周期性地采集并记录**被纳管系统**的运行状态指标，作为异常检测的基础。所有具体地址、端口、组件名、数量均来自被纳管系统的配置/适配器，而非 AI SRE 本体硬编码（SAS 的具体取值见附录「参考实例配置」，仅为示例）：
- **服务健康**：轮询被纳管系统配置的健康端点，记录 HTTP 状态码、响应时延、返回体状态。
- **前端/入口可用性**：检查被纳管系统各前端入口/服务端点的可访问性与关键页面渲染状态。
- **容器/进程**：监测被纳管系统各容器/服务的运行状态（Up/Exited/Restarting）、重启次数、资源占用（CPU/内存）。
- **数据库**：被纳管系统数据库的连接可用性、慢查询、连接池占用、复制/备份状态。
- **缓存/键值存储**：被纳管系统缓存/键值存储的内存使用、命中率、连接状态。
- **磁盘**：被纳管系统宿主与数据卷磁盘使用率、日志文件增长。
- **日志**：聚合被纳管系统的关键日志源，识别 ERROR/FATAL/panic 级别事件。
- **心跳**：确认各 Agent（含 AI SRE 自身）心跳存活与最近活动时间。
> 备注：此处「运行状态」均指**可用性/可靠性**信号，不覆盖功能正确性（详见本节「检测边界」说明）；对不产生可观测信号的功能缺陷，AI SRE 无法仅凭上述采集自动发现。

### F-SRE-002 异常与缺陷自动检测
在监控数据基础上，AI SRE 必须能自动识别异常，包括但不限于：
- 服务不可用（健康检查失败、容器退出、端口无响应）。
- 资源告警（磁盘 > 阈值、内存/CPU 持续高位、连接池耗尽）。
- 错误率/失败率异常升高（5xx 比例、接口失败率）。
- 日志中的异常模式（重复错误堆栈、panic、超时）。
> 备注：以上可自动识别范围均属**可用性/可靠性/错误率**类信号。对「返回 200 但结果数据错 / 页面空白但不抛错」等**不产生可观测信号的功能正确性**问题，**不在 F-SRE-002 可自动检测范围内**，由 QA 功能测试与 F-SRE-014 用户报障兜底（详见「检测边界」说明）。

### F-SRE-003 异常分级（P0-P3）
AI SRE 必须将检测到的异常/缺陷按既有缺陷分级标准映射为 P0-P3，并给出分级理由：
- **P0（致命）**：系统整体不可用、数据丢失风险、核心链路全断（如核心服务宕机、数据库不可用）。
- **P1（严重）**：核心功能不可用或严重降级、数据不一致（如单前端入口不可用、缓存/键值存储不可用）。
- **P2（一般）**：非核心功能受影响、资源逼近阈值、可降级运行。
- **P3（轻微）**：低风险、体验问题、非紧急告警。

### F-SRE-004 异常定位
对已检测并分级的异常，AI SRE 必须产出定位信息，至少包含：
- 受影响组件/容器/服务。
- 最近变更（部署 commit、配置变更）关联分析。
- 根因假设（如容器 OOM、磁盘写满、依赖服务不可达）。
- 建议处理动作（自愈 or 升级）。

### F-SRE-005 故障自愈（可自动修复项）
对低风险、可回滚、可恢复的故障，AI SRE 必须自动执行修复，并在修复后验证。可自动修复范围限定为：
- **重启容器**：对非数据层的无状态服务容器执行 restart。
- **清理磁盘**：清理可安全删除的临时文件、旧日志、孤儿镜像/卷（保留受保护数据）。
- **回滚部署**：自动回滚**仅当同时满足**（a）上一稳定版本曾通过 QA 且健康、（b）处于变更窗内、（c）已升级 PM 获软授权或受严格门禁；否则一律升级 DEVOPS 人工回滚（需有版本快照）。
- **释放资源**：清理僵尸进程、重建无状态连接池。
- **重启受控服务**：在安全前提下重启缓存/会话类等有状态但可快速恢复的服务（仅限非数据损坏场景）。

#### 自愈动作允许/禁止判定矩阵（Blocking B3 整改）

| 自愈动作 | 允许自动执行的条件 | 禁止自动执行（一律升级） | 升级目标 |
|----------|--------------------|--------------------------|----------|
| 重启容器 | 无状态服务；二次独立信号确认；冷却期内无重复 | 有状态/数据层容器；联动故障；无法确认根因 | DEVOPS |
| 清理磁盘 | 使用率 85%=P2；仅清理白名单内临时文件/旧日志/孤儿镜像卷（不触碰受保护卷） | 使用率 95%/写满=P0；受保护卷；正在调查/审计的日志 | DEVOPS |
| 连接池重建 | 无在途写；已确认非多服务联动故障 | 存在在途请求/写；疑似联动；无法确认非联动 | DEVOPS/DEV |
| 回滚部署 | 同时满足（a）上一稳定版本曾通过 QA 且健康（b）变更窗内（c）已升级 PM 获软授权或受严格门禁 | 任一条件不满足 | DEVOPS |
| 重启缓存/键值存储 | 仅缓存/会话用途；确认非持久队列数据源；非数据损坏 | 持久化数据源/队列；数据损坏信号；无法确认用途 | DEVOPS |

分级阈值：磁盘 85%=P2（可清理）；95%/写满=P0（升级，禁止清理受保护卷）。缓存/键值存储重启仅限缓存/会话且确认非持久队列源；「数据损坏」具体判据信号：RDB/AOF 等持久化文件损坏、持久队列长度异常增长或丢失、keyspace 意外清空、主从复制中断伴数据不一致。

**防自愈风暴（防抖门禁）**：自愈动作触发前须 ≥2 个独立信号佐证 + 冷却/退避期；同一服务自愈动作次数上限（默认 ≤ 3 次/小时），超限一律转升级人工，禁止继续自动重试。

### F-SRE-006 故障自愈边界（只能告警，禁止自动修复）
以下场景 AI SRE **不得**自动修复，只能告警升级：
- 涉及数据一致性/数据丢失风险的操作（数据库恢复、数据迁移、写坏回放）。
- 生产数据删除、表结构变更、索引重建。
- 多服务联动故障、网络分区、无法确认根因的复杂故障。
- 需要人工决策的配置变更、凭据/密钥轮换、安全事件。
- 涉及第三方/外部依赖不可用的场景。

### F-SRE-007 告警升级与人工介入
AI SRE 必须定义明确的升级时机与路径：
- **升级给 PM**：出现 P0/P1 缺陷、需要决策是否回滚/停机窗口、影响多 Agent 协作的任务冲突。
- **升级给 DEVOPS**：需要执行部署、回滚、基础设施变更（超出 AI SRE 自愈权限）。
- **升级给 DEV**：定位到明确代码缺陷、需修复的 bug（通过创建/关联 Issue）。
- **人工介入触发条件**：自愈失败、连续重试超过上限、异常持续超过阈值时间、同一异常复发达到次数上限。
- **通知去重与抑制**：升级通知须去重、节流，并按 P0/P1 收敛聚合（同一根因合并通知，避免重复 Issue 与告警疲劳）。
- 告警必须包含：异常摘要、分级、定位信息、已执行的自愈动作及结果、建议的人工处理步骤。

### F-SRE-008 多 Agent 团队协作接口
AI SRE 必须通过既定通信协议与其他 Agent 协作：
- **向 PM**：报告系统状态摘要、缺陷发现、升级请求、自愈结果。
- **向 DEV**：创建/关联 Issue（作为唯一真相源）、提供定位证据。
- **向 QA**：提供自愈后的验证请求、环境恢复确认。
- **向 DEVOPS**：提交部署/回滚/基础设施操作请求（超出自愈权限时）。
- **向 CHECKER**：提供运维动作记录供质检。
- **向 OPS**：同步部署配置与运行配置变更。
- 所有协作必须写回 GitHub Issue 与 Dashboard，保证「Issue 为唯一真相源」。

### F-SRE-009 Agent 生态落地（Blocking B2 整改）
AI SRE（及 OPS）必须注册进现有团队 Agent 生态：write_message.py 的 --from 枚举、agent-status 状态表、GitHub label、Dashboard 面板，方能收发团队消息、状态同步与协作。F-SRE-008 的协作接口以本项为前置依赖（前置 AC：AI SRE 已注册且能通过 write_message.py 收发消息）。统一命名：部署/基础设施变更对接 DEVOPS，纯运营值班与巡检对接 OPS。

### F-SRE-010 可部署性（Deployable）
AI SRE 必须以**自包含、可部署单元**交付，并可部署到任意新环境（新的主机、集群、云账号、本地环境），而非仅能在 SAS 现有环境内运行。具体要求：
- **交付物**：容器镜像（带版本与签名）+ 编排清单（docker-compose / helm chart 任一或两者）+ 一键接入脚本（bootstrap/onboard），三者缺一不可。
- **配置与代码分离**：运行所需的一切差异（目标系统地址、端口、路径、凭据引用、阈值、策略、告警通道）均通过配置文件/环境变量/Secret 注入，核心代码与镜像不含任何系统特定硬编码（包括 SAS 的拓扑/端口/路径/组件构成，SAS 仅以一份默认示例配置 profile 随发行附带，可删除/替换）。
- **凭配置即运行**：在空环境中，仅提供最小配置即可启动 AI SRE 并进入「待接入」状态，无需改动镜像或代码。
- **可移植性**：同一镜像可跨环境复用；不同环境仅差异在配置与 Secret。
- **可回滚部署**：AI SRE 自身具备版本化与可回滚能力（与前文 F-SRE-005 治理一致，AI SRE 自身部署/升级同样受变更窗与门禁约束）。

### F-SRE-011 系统接入与发现（Onboarding & Discovery）
AI SRE 通过**配置驱动 + 适配器插件模型**对新系统进行接入与组件发现建模，**不得硬编码 SAS 的拓扑/端口/路径**。具体要求：
- **接入方式**：新系统接入 = 新增一份系统配置 +（可选）注册一个适配器插件，**不改核心代码**。
- **组件发现与建模**：对目标系统自动发现并建模以下组件/资源类别（能力取决于加载的适配器）：
  - 服务（service）与容器（container）；
  - 数据库（如 PostgreSQL 等，只读连接用于监控）；
  - 缓存/键值存储（如 Redis）；
  - 日志源（log source）；
  - 健康端点（health endpoint）；
  - 磁盘/资源（disk / CPU / 内存）。
- **健康端点/端口/路径抽象化**：SAS 的 `:3000/api/health`、`:8080`、`:8081` 仅作为 SAS 实例配置中的示例值；AI SRE 从配置读取健康端点、端口与路径，不将任何具体地址写死。
- **无适配器时的降级**：对未提供专用适配器的系统，仍可通过通用 HTTP 健康探测 + 日志源 + 资源指标的最小配置接入；专用适配器作为可选增强。
- **接入原子性**：系统接入应可一次性完成并验证（发现组件、建立监控、产出初始清单），接入时间可度量。
- **适配器插件生命周期与安全**：适配器插件须带签名校验与最小权限声明、运行于独立进程/沙箱隔离；支持热加载与回滚；加载/校验失败时拒绝加载并保持既有能力可用（任一缺陷适配器不得攻陷或污染 AI SRE 实例及其纳管的其它系统）。
- **接入期凭证与安全边界**：新系统凭证经密钥管理/Secret 注入，不落盘明文；接入/发现期仅允许只读探测与白名单接口，不得触碰目标系统敏感卷/密钥/生产数据；接入脚本与适配器包需签名校验。

### F-SRE-012 自学习（Self-learning）
AI SRE 对新接入系统**学习基线指标与异常模式**，检测阈值与自愈策略随系统行为动态调整。具体要求：
- **学习三态**：每个接入系统在 AI SRE 内具有明确学习状态机——
  - **冷启动（Cold Start）**：接入初期，无该系统的历史基线，采用保守通用阈值，异常判定偏向「提示而非自动自愈」。
  - **预热（Warm-up）**：采集一段时间后，逐步拟合该系统的正常区间（时/日/周周期性、负载范围、延迟分布）。
  - **已学习（Learned）**：基线稳定，按系统特定阈值与异常模式执行检测与自愈，误报率显著下降。
- **三态迁移判据（可测）**：
  - 冷启动 → 预热：完成首轮组件发现与监控建立后进入预热，持续采集 ≥ N 个观测窗口（默认 N=7 个完整日窗口或等量小时窗口，可配置），且覆盖指标类别 ≥ M 类（服务健康/资源/日志/缓存/数据库等，默认 M=4）且无连续异常空窗。
  - 预热 → 已学习：最近连续 K 个观测窗口（默认 K=14 个）内基线波动 < X%（默认 X=20%，按指标类型分别度量）或误报率 < Y%（默认 Y=5%），且相邻窗口阈值变化 < Z%（默认 Z=5%）视为收敛。
- **动态调整**：检测阈值、异常判定规则、自愈策略随系统行为演化而自动更新（如流量增长后正常 CPU 区间上移）。
- **跨系统迁移学习先验**：可将已学习系统的先验知识（同类技术栈、通用异常模式、告警模板）迁移到新系统以缩短冷启动/预热周期；迁移发生前需标记来源，避免错误过拟合到异质系统；迁移效果以「达到已学习态所需观测窗口数减少率」或「冷启动→已学习总时长缩短率」度量。
- **学习可解释与可回退**：学习结果（阈值/规则/策略）须可解释、版本化，支持回退到上一稳定基线（如误学习导致误报，可手动/自动回退）。
- **投毒与漂移防护**：学习期剔除异常样本（被攻陷/故障系统的异常数据不参与基线拟合）；检测概念漂移并告警；基线重大变化须经可解释审计与门禁（默认需人工确认）。

### F-SRE-013 多系统/多租户支持
单个 AI SRE 实例可同时纳管**多个系统**，各系统之间的配置、凭证与策略**相互隔离**。具体要求：
- **多系统纳管**：一个实例同时管理 ≥1 个系统，每个系统独立建模、独立监控、独立告警、独立学习（状态机互不干扰）。
- **租户/系统隔离**：不同系统的配置、凭据（Secret）、自愈策略、告警通道、数据存储相互隔离，任一系统故障/被攻陷不越权影响其他系统。
- **凭证命名空间/密钥隔离**：各系统凭证以命名空间隔离，同一实例内系统 A 的凭证/令牌不得访问系统 B 的资源；跨租户访问一律拒绝并告警。
- **引用实例**：SAS 仅作为随发行附带的一份**默认示例配置 profile**（可删除/替换），其他系统以同等地位接入，SAS 不享有任何硬编码特权。
- **配额与横向扩展**：系统数量增长不应导致单实例性能/可靠性下降超阈值（见 NFR-X）；多实例部署可水平扩展分工纳管。
- **跨系统审计边界**：审计日志按系统隔离存储，仅追加写（append-only）防篡改；任一系统（含被攻陷系统）不得篡改/删除他系统审计记录；越权写审计尝试触发告警。

### F-SRE-014 用户报障接入（User Incident Intake）
AI SRE 必须提供**系统无关的用户报障接入**能力，作为对「功能不工作但系统健康运行」盲区的用户侧兜底入口（配合 QA 功能测试，详见本节「检测边界」说明）。用户在使用过程中发现功能不工作（即使系统健康指标正常），可经由报障通道反馈并交由 AI SRE 归一化、关联、分析与回执。报障接入内部各字段/通道均采用**通用命名**（不写死具体某套工单系统，通过通道配置/适配器接入）。具体约束：
- **Intake 通道（可配置）**：提供至少一个用户侧报障入口，支持 Web 表单 / IM / 邮件 / 工单 webhook 等（可配置；每通道通过统一 intake 接口收纳）。
- **归一化（Normalize）**：收到的报障内容须归一化为统一 incident 结构，结构化字段至少包含：受影响的系统标识（被纳管系统）、现象描述（自由文本）、影响范围/严重度初步估计、发生时间、报障者运营回执联系信息（用于回执，非业务用户 PII，采集与保留受 NFR-S「报障回执最小权限例外」约束）。来源通道与时间戳须保留以便追溯；**原始报文为可选项**——仅当取证/复核需要时保留，且按最小留存周期自动清理（不默认全量长期存档）。
- **关联 Issue**：incident 须关联或新建对应 GitHub Issue，延续「Issue 为唯一真相源」原则，保证与既有 PM 调度、DEV、QA 流程同源可见。
- **三分类定级（Triage）**：AI SRE 对归一化后的 incident 做**重复 / 已知 / 新建**三分类判定：
  - **重复（Duplicate）**：与同一根因/同现象既有 incident（或仍在抑制期/冷却期）重复，则合并、去重通知（对齐 F-SRE-007「通知去重与抑制」），仅更新既有记录；
  - **已知（Known）**：命中已在处理/已存在的 Issue 或已知根因（如已定位为某部署/回归），则合并到对应 Issue 并补充证据，不新建；
  - **新建（New）**：非重复亦非已知，作为新问题进入排查。
- **触发排查（Trigger）**：新建/未知 incident → 触发 AI SRE 针对该系统的**定向排查**（结合最近变更、可用性/可靠性信号识别是否已泄露可观测信号）：若 AI SRE 能定位到可观测信号则按既有升级路径处理；若属「静默/功能正确性」类（无可观测信号）则转 **DEV** 走代码层排查修复（经 Issue）。
- **反馈回执（Acknowledge & Close-loop）**：AI SRE 须向报障用户回执 incident 的处理状态（已受理 / 处理中 / 已修复），并在 Issue/Dashboard 可见闭环；状态变更（受理→定位→修复→关单）可追踪可回查。

## 3. 非功能需求（NFR）

### NFR-A 可用性（Availability）
- AI SRE 自身监控周期 ≤ 60 秒（关键健康检查），全量巡检周期 ≤ 5 分钟。
- AI SRE 单点故障不得影响业务系统本身运行（监控采集无侵入，不写入/阻塞主链路）；自愈动作须经门禁且可观测，触碰主链路的自愈动作仅限白名单内并在审计下执行。

### NFR-R 可靠性（Reliability）
- 自愈动作必须是幂等的，重复执行不产生副作用。
- 所有自愈动作必须可回滚或可撤销，执行前留存快照/状态。
- 告警不丢失：告警事件需持久化，升级链路失败时有重试机制。

### NFR-S 安全性（Security — 最小权限）
- AI SRE 仅拥有完成监控与自愈所需的最小权限（RBAC/最小权限原则）。
- 不得持有生产数据库写权限、不得访问业务用户隐私数据（业务用户 PII）。
- **报障回执最小权限例外（scope：F-SRE-014 / UC-SRE-016）**：为完成用户报障受理回执，AI SRE 可采集报障者运营回执联系信息，该项严格受如下约束，且**不属于**上述「访问业务用户 PII」之列：
  - 目的绑定：仅用于向报障者回执本 incident 的处理状态（已受理/处理中/已修复），不用于任何其它目的；
  - 仅回执用：联系信息不进入通用监控/告警/检测数据，不参与异常检测与基线建模；
  - 最小化存储：仅存报障通道供给的最小回执字段，不主动采集/挖掘额外个人属性；
  - 保留周期受限：联系信息按最小留存周期自动清理（默认随 incident 关单后 N 天内清除，可配置），不长期留存；
  - 脱敏/掩码展示：在 Issue/Dashboard/审计界面以脱敏或掩码形式展示（如尾号），不全量明文回写公共渠道；
  - 审计隔离：涉及该联系信息的读取/回执动作按 system 隔离写 append-only 审计，可追查不可篡改。
- 所有凭据通过密钥管理获取，不落盘明文；操作审计日志完整记录执行者、时间、动作、结果。
- 自愈操作白名单机制：仅白名单内动作可自动执行，白名单外一律升级人工；白名单动作须带显式授权与签名校验（动作需角色令牌 + 签名 allowlist 校验）。
- 紧急熔断开关（kill-switch）：一键停用所有自动自愈动作，切换为纯监控/告警模式。
- 每日异常动作上限：单实例每日自动自愈动作总数设上限，超限熔断并升级人工复核（防自愈动作被武器化/放大）。
- 审计边界：操作审计日志按系统隔离存储、仅追加写；被攻陷系统不得篡改/删除他系统审计记录，越权写审计触发告警。

### NFR-P 性能（Performance）
- 监控采集对被监控服务的额外负载 < 1% CPU。
- 异常检测从发生到产生告警的延迟 ≤ 2 分钟（P0/P1 场景）。
- 自愈动作单次执行时长受限（默认 ≤ 60 秒，超时转升级）。

### NFR-O 可观测性（Observability）
- 所有监控指标、检测事件、自愈动作、升级记录均可追溯、可查询。
- 提供统一的运行状态看板，支持历史趋势与告警统计。

### NFR-C 成本（Cost）
- 监控与检测优先复用现有基础设施与日志栈，避免引入高成本新增组件。
- 磁盘/日志保留周期可配置，避免监控数据无限增长占用存储。

### NFR-X 可移植性 / 可配置性 / 可扩展性（Portability / Configurability / Extensibility）
- **可移植性（Portability）**：AI SRE 核心镜像与代码不依赖任何单一系统/环境；跨环境迁移仅需替换配置与 Secret，代码零改动。
- **可配置性（Configurability）**：系统接入、组件拓扑、端口、路径、健康端点、阈值、自愈策略、告警通道全部配置化，无系统特定硬编码。
- **可扩展性（Extensibility）**：适配器插件模型支持以「注册插件」方式扩展对新组件类型/新系统的支持，不改核心代码；接入新系统成本应趋近「零/低代码」（仅配置，必要时加轻量适配器）。
- **多租户隔离（Multi-tenant Isolation）**：多系统纳管时，配置、凭证、策略、数据强隔离（逻辑隔离为主，必要时资源隔离）；租户之间无隐式共享状态。隔离的最小安全基线遵循 NFR-S（凭证命名空间隔离、跨租户访问拒绝、审计按系统隔离）；当出现高敏感/高合规要求的系统时，触发资源级隔离（独立进程/独立存储）。

## 4. 验收标准（Acceptance Criteria）

### F-SRE-001 验收标准
- AC-001：给定被纳管系统某服务进程停止运行，AI SRE 在 60 秒内采集到健康检查失败并记录状态，且在 2 分钟内产生告警事件。

### F-SRE-002 验收标准
- AC-002：模拟磁盘使用率超过设定阈值（如 85%），AI SRE 能自动识别该资源告警并在检测结果中标注异常类型与指标值。

### F-SRE-003 验收标准
- AC-003：注入一个核心服务完全不可用的故障，AI SRE 将其分级为 P0，并给出包含受影响组件与分级理由的分级结论。

### F-SRE-004 验收标准
- AC-004：对一个已知根因的故障（如某容器 OOM 退出），AI SRE 的定位信息能正确指向该容器并列出「内存不足」为根因假设之一。

### F-SRE-005 验收标准
- AC-005：对无状态服务容器执行重启自愈，AI SRE 执行 restart 后验证健康检查恢复为通过，并记录「已自愈」状态。
- AC-005a（磁盘清理）：模拟磁盘使用率超 85% 且存在白名单内可清理项，AI SRE 执行安全清理后磁盘恢复且未触碰受保护卷。
- AC-005b（回滚）：模拟新版本部署后健康检查失败且同时满足（a）上一稳定版本曾通过 QA 且健康（b）处于变更窗内（c）已获 PM 软授权，AI SRE 自动回滚到上一稳定版本并校验配置/依赖一致后恢复。
- AC-005c（缓存/键值存储重启）：模拟缓存/键值存储不可达且确认非持久队列源、非数据损坏，AI SRE 受限重启后恢复且不触碰持久化数据。
- AC-005d（释放资源/连接池重建）：模拟无状态连接池异常且无在途写，AI SRE 重建连接池后恢复；存在在途写时被拦截并升级（负向验证）。

### F-SRE-006 验收标准
- AC-006：对涉及生产数据库的故障，AI SRE 不执行任何写/删除/恢复动作，仅生成告警升级记录（验证最小权限与自愈白名单生效）。

### F-SRE-007 验收标准
- AC-007：同一自愈动作连续失败 3 次后，AI SRE 停止重试并生成发给 PM/DEVOPS 的升级告警，包含已执行动作与失败原因。

### F-SRE-008 验收标准
- AC-008：AI SRE 发现一个 P1 缺陷后，能在 GitHub 上创建/关联 Issue，并向 PM 发送通信消息，Dashboard 同步更新状态。

### F-SRE-010 验收标准
- AC-010：提供一个 AI SRE 交付包（镜像 + 编排清单 + 一键接入脚本），在全新空主机上仅凭最小配置（无 SAS）即能启动并进入「待接入」状态，全程不改镜像与代码。最小配置集合（minimal config）定义为：AI SRE 自身身份/监听端口、密钥管理引用（Secret 引用）、告警通道地址、（可选）至少一个被纳管系统的最小接入配置；不含任何 SAS 特定项。

### F-SRE-011 验收标准
- AC-011：给定一个新系统（仅一份配置 + 实例描述，不含 AI SRE 代码改动），AI SRE 能完成其组件发现与建模，产出服务/容器/数据库/日志源/健康端点/磁盘资源清单；SAS 的 `:3000`、`:8080`、`:8081` 等地址未出现在 AI SRE 核心代码/镜像中。

### F-SRE-012 验收标准
- AC-012：对一个新系统，AI SRE 在接入后经历冷启动 → 预热 → 已学习三态迁移，迁移判据可测且可独立验证：
  - **冷启动 → 预热**：完成首轮组件发现与监控建立后进入预热，持续采集 ≥ N 个观测窗口（默认 N=7 个完整日窗口，可配置），覆盖指标类别 ≥ M 类（默认 M=4：服务健康/资源/日志/缓存或数据库）且无连续异常空窗。
  - **预热 → 已学习**：最近连续 K 个观测窗口（默认 K=14）内基线波动 < X%（默认 X=20%，按指标类型分别度量）或误报率 < Y%（默认 Y=5%），且相邻窗口阈值变化 < Z%（默认 Z=5%）视为收敛。
  - **跨系统迁移先验**：从同类已学习系统迁移先验后，达到「已学习」所需观测窗口数较无先验冷启动减少 ≥ 25%，或冷启动→已学习总时长缩短 ≥ 25%（QA 以同构样本对照验证）。
  - **学习结果版本化与回退**：学习结果（阈值/规则/策略）可版本化；注入错误基线后可回退到上一稳定版本并验证误报率恢复。
  - 随系统行为变化自动更新检测阈值（如流量增长后正常 CPU 区间上移），且该更新可追溯。

### F-SRE-013 验收标准
- AC-013：单实例同时纳管两个独立系统（含 SAS），两系统的凭证、策略、告警通道、学习状态互不可见；任一系统故障不影响另一系统监控，SAS 无任何硬编码特权。
- AC-013a（负向，横向越权遏制）：以系统 A 的凭证/令牌尝试访问系统 B 的资源（配置、凭证、数据、审计日志）应被拒绝并触发告警。

### F-SRE-014 验收标准
- AC-014：给定一条用户报障（如某接口功能不工作、无可观测信号），将新建与重复/已知两类报障分开验收（见 AC-014a / AC-014b）；异常流（通道不可用、报文缺关键字段、回执失败）在 UC-SRE-016 覆盖。
- AC-014a（主流程，新建）：给定一条**新建**用户报障（如某接口功能不工作、无可观测丢错信号），AI SRE 能将其归一化为带完整性字段的 incident（含系统标识、现象、时间、报障者运营回执联系信息——采集与保留符合 NFR-S「报障回执最小权限例外」），关联/创建对应 GitHub Issue，完成三分类判定为「新建」，触发该系统的定向排查或经 Issue 转 DEV，并对报障用户回执“已受理”及后续处理状态（受理→定位→修复→关单）可追踪。
- AC-014b（负向主流程，重复/已知）：给定一条与既有 incident（同一根因/同现象）**重复**或在处理中的**已知**报障，AI SRE 将其归并为既有 incident/对应 Issue，去重合并通知、补充证据，**不重复新建 Issue/incident**，且不产生重复告警（符合 F-SRE-007 去重与抑制）。

## 5. 范围外（Out of Scope）

- 不做业务功能开发、不改业务代码（代码修复由 DEV 负责）。
- 不替代 PM 的调度决策，不替代 DEVOPS 的部署规划与执行（仅在其授权范围内执行受限自愈）。
- 不处理数据库 Schema 变更、数据迁移、数据清洗等数据工程任务。
- 不做安全渗透测试、合规审计（可检测异常并升级，但不执行安全修复）。
- 不做用户行为分析、业务指标分析（仅面向系统运维指标）。
- **不检测「功能正确性」本身**：AI SRE 验证的是可用性/可靠性，不验证业务逻辑是否正确、结果数据是否正确（详见 §2「检测边界」）。功能正确性由 QA 功能测试负责，用户侧发现的功能问题经 F-SRE-014 用户报障接入补位；AI SRE 仅在功能缺陷泄露可观测信号（抛错/5xx/错误率升高/DB 报错）时“顺带”发现，不覆盖静默 bug。
- 不承担跨系统/外部第三方服务的修复（仅检测与告警）。
- 不自建新的监控告警平台取代现有日志/监控栈（优先复用，仅在必要时补充 Agent 逻辑）。
- 不执行任何超出最小权限白名单的自动化操作。
- **不承诺零配置接入**：接入新系统仍需至少提供一份系统配置/凭证引用；不提供「完全无输入、纯黑盒自动逆向」能力。
- **不自动逆向未知黑盒系统**：对无任何配置、无适配器、无健康端点/日志源可探测的系统，不做逐接口自动化逆向工程或协议猜测（仅可做最小通用探测并提示人工补充配置）。
- **不替代目标系统自身的架构/代码改造**：AI SRE 只做监控/检测/自愈/告警，不负责改造被纳管系统的代码、拓扑或部署方式以适配 AI SRE。
- **AI SRE 自身维护归属**：AI SRE 自身的运行时运维、代码/自愈配置变更 review、AI SRE 自身出问题时的回滚，由 DEVOPS 与 PM 既有角色接管（AI SRE 不自运维自身）。

### 问题清单

#### Blocking（必须整改，否则不进入下阶段）

- **B1｜自愈回滚权责内部矛盾（F-SRE-005 vs F-SRE-007/范围外）**
  - 问题：F-005/UC-004 允许 AI SRE 对新部署健康检查失败**自动回滚**；F-007 却规定「升级给 DEVOPS：需要执行部署、**回滚**（超出 AI SRE 自愈权限）」；范围外又写「不替代 DEVOPS…仅授权范围内执行受限自愈」。同一「回滚」在文档内被同时判给 AI SRE 自动执行与 DEVOPS 人工执行，且未经 SVA 门（现有任何对生产的回滚须 QA 签署、由 DEVOPS/OPS 执行）。
  - 建议：在**需求层**明确回滚权属——建议「自动回滚」仅在最高授权下、且须满足（a）存在上一稳定版本**且曾通过 QA**、（b）发布窗/变更窗内、（c）先升级 PM 获得软授权或受严格门禁约束；否则回滚一律升级 DEVOPS。删除或拆分 UC-004 的自动回滚主张，避免一句话既是自愈又是 DEVOPS 职责。
- **B2｜AI SRE（与 OPS）Agent 未注册，协作接口不可落地**
  - 问题：Issue #370 明述「与现有多 Agent 团队协作」，F-SRE-008 全部依赖经 write_message.py 通信并同步 agent-status/GitHub label/Dashboard。但现有 `skills/agent-communication/scripts/write_message.py` 的 `--from` 枚举仅 {PM,DEV,QA,DEVOPS,CHECKER,ARCH,REQ}，**不含 AI SRE 也不含 OPS**；agent-status、GitHub label、Dashboard 面板亦无 AI SRE。F-SRE-008 在现工具下报错，无法验证，直接导致 AC-008 不可测。
  - 建议：REQ 增补一项「Agent 生态落地需求」到规格（或单列协作接口章节）：新增并注册 AI SRE Agent 名（脚本枚举、agent-status、GitHub label、Dashboard 面板、通信反 Side-effct 校验）；并解决文档内 OPS/DEVOPS 命名混用（背景/F-008 用 OPS，其余用 DEVOPS）——明确发起部署 vs 基础设施变更分别对接谁。将「AI SRE 已注册且能收发 write_message」列为 F-008 的前置 AC。
- **B3｜自愈 vs 告警升级边界在多处模糊且有数据丢失缺口**
  - 问题：a) F-005「重建无状态连接池/释放资源」与 F-006「多服务联动、无法确认根因的复杂故障不得自愈」边界重叠——在 prod 重建连接池会中断在途请求，可能是相互依赖的多服务联动；b) 磁盘仅设单一阈值（AC-002/UC-003 视 85% 为 P2 可清理），但「磁盘写满→数据丢失风险」按 F-003 应为 P0 不得自愈，文档缺「磁盘满=P0 升级、禁止清理触碰受保护卷」的升级档；c) Redis 在 F-005 可限重启，但 F-006 又禁数据一致性风险操作，需明确判据。
  - 建议：为每类自愈动作补充「允许/禁止」判定矩阵 + 触发升级的具体判据（连接池重建仅限无在途写、先确认非联动故障；磁盘分层阈值 85%=P2 清理、95%/写满=P0 升级禁止清卷；Redis 重启仅限缓存/会话且确认非持久队列数据源）。

#### Major（强烈建议整改）

- **M1｜自愈误判/抖动/风暴无保护**：健康探针瞬闪或误报可能触发对**健康服务**的多余 restart/回滚，缺「二次独立信号确认」「no-flap/冷却期」「自愈频率上限」。仅 UC-012 异常流提「复核排除」，无统一防抖门禁。建议：自愈前须 ≥2 个独立信号佐证 + 冷却/退避 + 单服务自愈次数/小时上限（超限转升级，防自愈风暴）。
- **M2｜回滚正确性缺口**：UC-004 前置只要求「有上一稳定版本快照」，未要求上一版本**曾经 QA 签收且健康**——否则可能回滚进另一个已坏的版本；也未处理「回滚后配置漂移/依赖不齐」。建议：回滚目标须命中「最近一次 QA 通过」的版本集，回滚后校验配置与依赖一致性。
- **M3｜安全：自愈动作成为攻击面 + 最小权限粒度不足**：若 AI SRE 被攻陷，其可自动 tigger 大量 prod restart/回滚/清理（武器化/放大攻击）。NFR-S 仅笼统「最小权限」，未按动作类映射角色、无可带签名白名单（动作需角色令牌+签名 allowlist 校验）、无干跑/异常上限/紧急熔断开关。建议：自愈动作与凭证分离、动作白名单带显式授权与签名、增加紧急 kill-switch 与每日异常动作上限。
- **M4｜数据一致性判据缺失（Redis「数据损坏」、DB 只读基线）**：UC-011 要 AI SRE「判断是否数据损坏」但 F/NFR 未给判据；NFR-S 说无 prod DB 写权限但未定义「只读连接」作为能力基线。建议：定义只读数据源、判定数据损坏的具体信号、以及「自愈触碰有状态服务」的硬约束。
- **M5｜生产自愈绕过 SVA/发布窗治理**：UC-002/003/004/011 的自动 restart/rollback/清理在 prod 直接生效，未定义与 SVA gate、QA 签收、变更窗/发布冻结/停机窗口（F-007 提了「停机窗口」但无联动机制）的关系。建议：需求层给出「何时自动动作免门禁、何时必须先经 PM 软授权」的治理规则，避免自愈成为灰色地带。
- **M6｜AC/测试覆盖不足**：主 F-005（含重启容器/清理磁盘/回滚/释放资源/重启 Redis 5 类）仅 AC-005（restart）一条，回滚、Redis、磁盘清理均无对应 AC；缺「白名单外动作被拦截」的负向 AC（仅 AC-006 DB 一例）；缺升级链路失败时告警持久化/补发的 AC。建议：按动作类各补 1 AC，并增加负向与失败路径 AC。

#### Minor（可后续完善，不阻塞）

- **m1｜UC↔F 追溯缺失**：12 用例与 8 功能对应不显式呈现（UC-009/010 无唯一归属 F，UC-006 有多个候选），建议加 UC→F 追溯列或矩阵，保证每条功能至少被一条用例+AC 覆盖。

### 问题清单

#### Blocking（必须整改，否则不进入下阶段）

- **B1｜系统无关原则未落实到既有核心需求（SAS 硬编码残留矛盾）**
  - 问题：§1 声明「所有功能需求均以系统无关为原则表述、SAS 拓扑/端口/路径不写死进本体」，F-SRE-011 明确「不得硬编码 SAS 的拓扑/端口/路径」，NFR-X 要求「无系统特定硬编码」；但 F-SRE-001 正文仍以「监测 13 个容器」「轮询 :3000/api/health」「admin（:8080）/portal（:8081）」「PostgreSQL/Redis」作为规范性需求，UC-SRE-001~012 亦全按 SAS 编写，均未标注「以 SAS 为例」。实现者若按 F-SRE-001 字面实现，将直接违反 F-SRE-011/NFR-X。
  - 另：F-SRE-013「SAS 作为默认**内置**的一个参考实例」与 F-SRE-010「核心代码与镜像不含任何系统特定硬编码」矛盾——「内置」本身就是一种硬编码特权，与「SAS 不享有任何硬编码特权」相抵。
  - 建议：将 F-SRE-001~008 中所有 SAS 具体值（容器数、端口、路径、组件名）显式标注为「SAS 实例示例值」或改为占位符 + 配置引用；UC-SRE-001~012 表头/正文标注「以 SAS 为例」；明确「默认内置 SAS」指「随镜像附带一份 SAS 示例配置」而非「SAS 逻辑内置于镜像/代码」。
- **B2｜自学习验收标准 AC-012 不可量化、不可独立验证**
  - 问题：「可学习」是 v0.3.0 三大核心新目标之一，但 AC-012「经历冷启动→预热→已学习三态」「迁移先验以缩短冷启动周期」无任何量化标准：无状态迁移判据（采集数据量/时长/样本数）、无冷启动→已学习的周期目标、「缩短冷启动周期」无度量方式（缩短多少、如何对比）、「自动更新阈值」无验收判据。QA 无法据此独立判定通过/不通过。
  - 建议：为学习三态定义可度量迁移条件（如「预热→已学习：连续 N 天基线波动 < X% 或误报率 < Y%」），为「迁移先验缩短冷启动周期」定义量化指标（如「冷启动周期较无先验缩短 ≥ Z%」或「达已学习所需数据量减少 ≥ W%」），并补「学习结果版本化与回退」的正向 AC。

#### Major（强烈建议整改）

- **M1｜适配器插件生命周期/安全未定义**：F-SRE-011 仅「注册一个适配器插件，不改核心代码」，未定义适配器的加载方式（热加载 vs 重启）、版本/签名校验、插件隔离与权限边界。恶意或缺陷适配器可借插件机制攻陷/污染整个 AI SRE 实例及所有纳管系统。建议补：适配器须带签名校验、最小权限声明、独立进程/沙箱隔离、热加载与回滚生命周期。

- **M3｜新系统接入的凭证注入与安全边界缺失**：F-SRE-011 接入流程未明确新系统凭证如何安全注入（经 Secret/密钥管理而非落盘明文），未定义接入/发现期的安全边界（只读探测、不得触碰目标系统敏感卷/密钥/生产数据）。NFR-S 的「最小权限」为全局表述且偏 SAS 语境，未下沉到接入动作。建议补：接入期仅允许只读探测与白名单接口，凭证经密钥管理注入，接入脚本需签名。

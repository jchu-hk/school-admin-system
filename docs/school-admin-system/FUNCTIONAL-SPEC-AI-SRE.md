## 1. 需求背景与目标

School Admin System 当前由多 Agent 团队（PM/DEV/QA/CHECKER/DEVOPS/OPS/ARCH/REQ）协作维护，但系统运行状态的监控、异常发现与故障恢复仍依赖人工被动触发，响应链路长、存在滞后。随着系统复杂度上升（13 个 Docker 容器、PostgreSQL/Redis/文件存储、三个前端入口），需要一个常驻的「AI SRE 运维 Agent」，对系统运营状态进行自主感知，自动完成异常/缺陷的检测、分级与定位，并对可自愈故障执行自动化修复、对不可自愈故障进行告警升级。

本规格旨在为 AI SRE Agent 定义清晰的职责边界与协作接口，使其成为团队中「全天候值守、先于用户感知问题、先于人工处理简单故障」的运维角色，同时与现有 PM 调度、DEV 修 bug、QA 验证、DEVOPS 部署的流程无缝衔接。

## 2. 功能边界（Functional Scope）

### F-SRE-001 运行状态自主监控
AI SRE 必须周期性地采集并记录以下运行状态指标，作为异常检测的基础：
- **Backend 健康**：轮询 `:3000/api/health`，记录 HTTP 状态码、响应时延、返回体状态。
- **前端可用性**：检查 admin 前端（:8080）与 portal 前端（:8081）的可访问性与关键页面渲染状态。
- **Docker 容器**：监测 13 个容器的运行状态（Up/Exited/Restarting）、重启次数、资源占用（CPU/内存）。
- **数据库**：PostgreSQL 连接可用性、慢查询、连接池占用、复制/备份状态。
- **Redis**：内存使用、命中率、连接状态。
- **磁盘**：宿主与数据卷磁盘使用率、日志文件增长。
- **日志**：聚合关键日志流，识别 ERROR/FATAL/panic 级别事件。
- **心跳**：确认各 Agent（含 AI SRE 自身）心跳存活与最近活动时间。

### F-SRE-002 异常与缺陷自动检测
在监控数据基础上，AI SRE 必须能自动识别异常，包括但不限于：
- 服务不可用（健康检查失败、容器退出、端口无响应）。
- 资源告警（磁盘 > 阈值、内存/CPU 持续高位、连接池耗尽）。
- 错误率/失败率异常升高（5xx 比例、接口失败率）。
- 日志中的异常模式（重复错误堆栈、panic、超时）。

### F-SRE-003 异常分级（P0-P3）
AI SRE 必须将检测到的异常/缺陷按既有缺陷分级标准映射为 P0-P3，并给出分级理由：
- **P0（致命）**：系统整体不可用、数据丢失风险、核心链路全断（如 Backend 宕机、数据库不可用）。
- **P1（严重）**：核心功能不可用或严重降级、数据不一致（如单前端入口不可用、Redis 不可用）。
- **P2（一般）**：非核心功能受影响、资源逼近阈值、可降级运行。
- **P3（轻微）**：低风险、体验问题、非紧急告警。

### F-SRE-004 异常定位
对已检测并分级的异常，AI SRE 必须产出定位信息，至少包含：
- 受影响组件/容器/服务。
- 最近变更（部署 commit、配置变更）关联分析。
- 根因假设（如容器 OOM、磁盘写满、依赖服务不可达）。
- 建议处理动作（自愈 or 升级）。

### F-SRE-005 故障自愈（可自动修复项）
对低风险、可回滚、可恢复的故障，AI SRE 必须自动执行修复，并在修复后验证。可自动修复范围限定为：
- **重启容器**：对非数据层的无状态服务容器执行 restart。
- **清理磁盘**：清理可安全删除的临时文件、旧日志、孤儿镜像/卷（保留受保护数据）。
- **回滚部署**：自动回滚**仅当同时满足**（a）上一稳定版本曾通过 QA 且健康、（b）处于变更窗内、（c）已升级 PM 获软授权或受严格门禁；否则一律升级 DEVOPS 人工回滚（需有版本快照）。
- **释放资源**：清理僵尸进程、重建无状态连接池。
- **重启受控服务**：在安全前提下重启 Redis 等有状态但可快速恢复的服务（仅限非数据损坏场景）。

#### 自愈动作允许/禁止判定矩阵（Blocking B3 整改）

| 自愈动作 | 允许自动执行的条件 | 禁止自动执行（一律升级） | 升级目标 |
|----------|--------------------|--------------------------|----------|
| 重启容器 | 无状态服务；二次独立信号确认；冷却期内无重复 | 有状态/数据层容器；联动故障；无法确认根因 | DEVOPS |
| 清理磁盘 | 使用率 85%=P2；仅清理白名单内临时文件/旧日志/孤儿镜像卷（不触碰受保护卷） | 使用率 95%/写满=P0；受保护卷；正在调查/审计的日志 | DEVOPS |
| 连接池重建 | 无在途写；已确认非多服务联动故障 | 存在在途请求/写；疑似联动；无法确认非联动 | DEVOPS/DEV |
| 回滚部署 | 同时满足（a）上一稳定版本曾通过 QA 且健康（b）变更窗内（c）已升级 PM 获软授权或受严格门禁 | 任一条件不满足 | DEVOPS |
| 重启 Redis | 仅缓存/会话用途；确认非持久队列数据源；非数据损坏 | 持久化数据源/队列；数据损坏信号；无法确认用途 | DEVOPS |

分级阈值：磁盘 85%=P2（可清理）；95%/写满=P0（升级，禁止清理受保护卷）。Redis 重启仅限缓存/会话且确认非持久队列源。

### F-SRE-006 故障自愈边界（只能告警，禁止自动修复）
以下场景 AI SRE **不得**自动修复，只能告警升级：
- 涉及数据一致性/数据丢失风险的操作（数据库恢复、数据迁移、写坏回放）。
- 生产数据删除、表结构变更、索引重建。
- 多服务联动故障、网络分区、无法确认根因的复杂故障。
- 需要人工决策的配置变更、凭据/密钥轮换、安全事件。
- 涉及第三方/外部依赖不可用的场景。

### F-SRE-007 告警升级与人工介入
AI SRE 必须定义明确的升级时机与路径：
- **升级给 PM**：出现 P0/P1 缺陷、需要决策是否回滚/停机窗口、影响多 Agent 协作的任务冲突。
- **升级给 DEVOPS**：需要执行部署、回滚、基础设施变更（超出 AI SRE 自愈权限）。
- **升级给 DEV**：定位到明确代码缺陷、需修复的 bug（通过创建/关联 Issue）。
- **人工介入触发条件**：自愈失败、连续重试超过上限、异常持续超过阈值时间、同一异常复发达到次数上限。
- 告警必须包含：异常摘要、分级、定位信息、已执行的自愈动作及结果、建议的人工处理步骤。

### F-SRE-008 多 Agent 团队协作接口
AI SRE 必须通过既定通信协议与其他 Agent 协作：
- **向 PM**：报告系统状态摘要、缺陷发现、升级请求、自愈结果。
- **向 DEV**：创建/关联 Issue（作为唯一真相源）、提供定位证据。
- **向 QA**：提供自愈后的验证请求、环境恢复确认。
- **向 DEVOPS**：提交部署/回滚/基础设施操作请求（超出自愈权限时）。
- **向 CHECKER**：提供运维动作记录供质检。
- **向 OPS**：同步部署配置与运行配置变更。
- 所有协作必须写回 GitHub Issue 与 Dashboard，保证「Issue 为唯一真相源」。

### F-SRE-009 Agent 生态落地（Blocking B2 整改）
AI SRE（及 OPS）必须注册进现有团队 Agent 生态：write_message.py 的 --from 枚举、agent-status 状态表、GitHub label、Dashboard 面板，方能收发团队消息、状态同步与协作。F-SRE-008 的协作接口以本项为前置依赖（前置 AC：AI SRE 已注册且能通过 write_message.py 收发消息）。统一命名：部署/基础设施变更对接 DEVOPS，纯运营值班与巡检对接 OPS。

## 3. 非功能需求（NFR）

### NFR-A 可用性（Availability）
- AI SRE 自身监控周期 ≤ 60 秒（关键健康检查），全量巡检周期 ≤ 5 分钟。
- AI SRE 单点故障不得影响业务系统本身运行（旁路监控，不侵入主链路）。

### NFR-R 可靠性（Reliability）
- 自愈动作必须是幂等的，重复执行不产生副作用。
- 所有自愈动作必须可回滚或可撤销，执行前留存快照/状态。
- 告警不丢失：告警事件需持久化，升级链路失败时有重试机制。

### NFR-S 安全性（Security — 最小权限）
- AI SRE 仅拥有完成监控与自愈所需的最小权限（RBAC/最小权限原则）。
- 不得持有生产数据库写权限、不得访问用户隐私数据（PII）。
- 所有凭据通过密钥管理获取，不落盘明文；操作审计日志完整记录执行者、时间、动作、结果。
- 自愈操作白名单机制：仅白名单内动作可自动执行，白名单外一律升级人工。

### NFR-P 性能（Performance）
- 监控采集对被监控服务的额外负载 < 1% CPU。
- 异常检测从发生到产生告警的延迟 ≤ 2 分钟（P0/P1 场景）。
- 自愈动作单次执行时长受限（默认 ≤ 60 秒，超时转升级）。

### NFR-O 可观测性（Observability）
- 所有监控指标、检测事件、自愈动作、升级记录均可追溯、可查询。
- 提供统一的运行状态看板，支持历史趋势与告警统计。

### NFR-C 成本（Cost）
- 监控与检测优先复用现有基础设施与日志栈，避免引入高成本新增组件。
- 磁盘/日志保留周期可配置，避免监控数据无限增长占用存储。

## 4. 验收标准（Acceptance Criteria）

### F-SRE-001 验收标准
- AC-001：给定 Backend 进程停止运行，AI SRE 在 60 秒内采集到健康检查失败并记录状态，且在 2 分钟内产生告警事件。

### F-SRE-002 验收标准
- AC-002：模拟磁盘使用率超过设定阈值（如 85%），AI SRE 能自动识别该资源告警并在检测结果中标注异常类型与指标值。

### F-SRE-003 验收标准
- AC-003：注入一个 Backend 完全不可用的故障，AI SRE 将其分级为 P0，并给出包含受影响组件与分级理由的分级结论。

### F-SRE-004 验收标准
- AC-004：对一个已知根因的故障（如某容器 OOM 退出），AI SRE 的定位信息能正确指向该容器并列出「内存不足」为根因假设之一。

### F-SRE-005 验收标准
- AC-005：对无状态服务容器执行重启自愈，AI SRE 执行 restart 后验证健康检查恢复为通过，并记录「已自愈」状态。

### F-SRE-006 验收标准
- AC-006：对涉及生产数据库的故障，AI SRE 不执行任何写/删除/恢复动作，仅生成告警升级记录（验证最小权限与自愈白名单生效）。

### F-SRE-007 验收标准
- AC-007：同一自愈动作连续失败 3 次后，AI SRE 停止重试并生成发给 PM/DEVOPS 的升级告警，包含已执行动作与失败原因。

### F-SRE-008 验收标准
- AC-008：AI SRE 发现一个 P1 缺陷后，能在 GitHub 上创建/关联 Issue，并向 PM 发送通信消息，Dashboard 同步更新状态。

## 5. 范围外（Out of Scope）

- 不做业务功能开发、不改业务代码（代码修复由 DEV 负责）。
- 不替代 PM 的调度决策，不替代 DEVOPS 的部署规划与执行（仅在其授权范围内执行受限自愈）。
- 不处理数据库 Schema 变更、数据迁移、数据清洗等数据工程任务。
- 不做安全渗透测试、合规审计（可检测异常并升级，但不执行安全修复）。
- 不做用户行为分析、业务指标分析（仅面向系统运维指标）。
- 不承担跨系统/外部第三方服务的修复（仅检测与告警）。
- 不自建新的监控告警平台取代现有日志/监控栈（优先复用，仅在必要时补充 Agent 逻辑）。
- 不执行任何超出最小权限白名单的自动化操作。

## 6. 用例表

| 用例ID | 名称 | 触发条件 | 执行角色 | 前置条件 | 主流程 | 异常流程 |
|--------|------|----------|----------|----------|--------|----------|
| UC-SRE-001 | 定时全量健康巡检 | 巡检周期定时器触发 | AI SRE | 监控采集权限就绪；服务正常运行 | 1. 采集 backend/admin/portal/DB/Redis/磁盘/日志/心跳数据；2. 与基线比对；3. 正常则记录快照；4. 有异常则转异常检测 | 采集超时/失败 → 标记采集失败并重试，连续失败转 PM |
| UC-SRE-002 | Backend 宕机检测与自愈 | 健康检查连续 N 次失败 | AI SRE | Backend 为无状态服务；重启在白名单内 | 1. 确认 :3000/api/health 失败；2. 分级 P0；3. 定位容器/进程；4. 执行容器 restart；5. 验证健康恢复；6. 记录自愈结果 | 重启后仍未恢复 → 停止重试，升级给 DEVOPS/PM |
| UC-SRE-003 | 磁盘空间告警与清理 | 磁盘使用率超阈值 | AI SRE | 清理规则（白名单目录）已配置 | 1. 检测磁盘 > 阈值；2. 分级 P2；3. 识别可清理项（旧日志/临时文件）；4. 执行安全清理；5. 复核磁盘恢复 | 无可安全清理项 → 升级 DEVOPS 扩容 |
| UC-SRE-004 | 新版本部署后回滚（受限自动） | 新版本部署后健康检查失败 | AI SRE | 上一稳定版本曾通过 QA 且健康；处于变更窗内；已升级 PM 获软授权或受严格门禁；回滚在白名单内 | 1. 检测部署后健康异常；2. 关联最近部署 commit；3. 判定为部署引入；4. 前置判定：确认（a）上一稳定版本曾通过 QA 且健康、（b）处于变更窗内、（c）已升级 PM 获软授权或受严格门禁；5. 满足则执行自动回滚到上一版本，否则升级 DEVOPS 人工回滚；6. 验证恢复；7. 记录并同步 PM | 回滚失败 → 立即升级 DEVOPS，标注紧急 |
| UC-SRE-005 | 数据库异常告警升级 | DB 连接/慢查询异常 | AI SRE | 无 DB 写权限；仅监控 | 1. 检测 DB 不可用/连接池耗尽；2. 分级 P0/P1；3. 定位并产出根因假设；4. 因超出白名单，仅生成告警 | 告警发送失败 → 持久化重试，保底落地 Issue |
| UC-SRE-006 | 日志错误模式识别 | 日志聚合出现 ERROR 簇 | AI SRE | 日志采集管道可用 | 1. 聚合 ERROR/FATAL 日志；2. 识别重复堆栈/模式；3. 分级并定位；4. 产出告警/建议动作 | 日志缺失/管道中断 → 标记可观测性告警 |
| UC-SRE-007 | P1 缺陷创建 Issue 并升级 | 检测到需人工修复的 P1 缺陷 | AI SRE | GitHub 权限；PM 通信协议可用 | 1. 检测并分级 P1；2. 定位根因；3. 创建/关联 Issue（含证据）；4. 通知 PM；5. 同步 Dashboard | Issue 创建失败 → 重试，仍失败则直接通知 PM |
| UC-SRE-008 | 自愈失败升级人工 | 同一自愈动作重试达上限 | AI SRE | 重试上限已配置（如 3 次） | 1. 自愈动作失败；2. 按策略重试；3. 达上限后停止；4. 生成升级告警（含失败原因）；5. 通知 PM/DEVOPS | 升级链路不可用 → 落盘待恢复后补发 |
| UC-SRE-009 | 心跳监测与 Agent 失联告警 | 某 Agent 心跳超时 | AI SRE | 心跳上报机制运行中 | 1. 检测某 Agent 心跳超时；2. 分级 P2；3. 记录失联时长；4. 通知 PM；5. 恢复后记录 | AI SRE 自身心跳异常 → 由 PM 侧兜底检测 |
| UC-SRE-010 | 自愈动作审计与质检 | 每次自愈动作完成 | AI SRE + CHECKER | 审计日志开启 | 1. 记录动作/时间/结果；2. 写入审计日志；3. 提交 CHECKER 质检；4. 质检结论回写 | 审计日志写入失败 → 标记并阻止后续自愈直至恢复 |

### 问题清单

#### Blocking（必须整改，否则不进入下阶段）

- **B1｜自愈回滚权责内部矛盾（F-SRE-005 vs F-SRE-007/范围外）**
  - 问题：F-005/UC-004 允许 AI SRE 对新部署健康检查失败**自动回滚**；F-007 却规定「升级给 DEVOPS：需要执行部署、**回滚**（超出 AI SRE 自愈权限）」；范围外又写「不替代 DEVOPS…仅授权范围内执行受限自愈」。同一「回滚」在文档内被同时判给 AI SRE 自动执行与 DEVOPS 人工执行，且未经 SVA 门（现有任何对生产的回滚须 QA 签署、由 DEVOPS/OPS 执行）。
  - 建议：在**需求层**明确回滚权属——建议「自动回滚」仅在最高授权下、且须满足（a）存在上一稳定版本**且曾通过 QA**、（b）发布窗/变更窗内、（c）先升级 PM 获得软授权或受严格门禁约束；否则回滚一律升级 DEVOPS。删除或拆分 UC-004 的自动回滚主张，避免一句话既是自愈又是 DEVOPS 职责。
- **B2｜AI SRE（与 OPS）Agent 未注册，协作接口不可落地**
  - 问题：Issue #370 明述「与现有多 Agent 团队协作」，F-SRE-008 全部依赖经 write_message.py 通信并同步 agent-status/GitHub label/Dashboard。但现有 `skills/agent-communication/scripts/write_message.py` 的 `--from` 枚举仅 {PM,DEV,QA,DEVOPS,CHECKER,ARCH,REQ}，**不含 AI SRE 也不含 OPS**；agent-status、GitHub label、Dashboard 面板亦无 AI SRE。F-SRE-008 在现工具下报错，无法验证，直接导致 AC-008 不可测。
  - 建议：REQ 增补一项「Agent 生态落地需求」到规格（或单列协作接口章节）：新增并注册 AI SRE Agent 名（脚本枚举、agent-status、GitHub label、Dashboard 面板、通信反 Side-effct 校验）；并解决文档内 OPS/DEVOPS 命名混用（背景/F-008 用 OPS，其余用 DEVOPS）——明确发起部署 vs 基础设施变更分别对接谁。将「AI SRE 已注册且能收发 write_message」列为 F-008 的前置 AC。
- **B3｜自愈 vs 告警升级边界在多处模糊且有数据丢失缺口**
  - 问题：a) F-005「重建无状态连接池/释放资源」与 F-006「多服务联动、无法确认根因的复杂故障不得自愈」边界重叠——在 prod 重建连接池会中断在途请求，可能是相互依赖的多服务联动；b) 磁盘仅设单一阈值（AC-002/UC-003 视 85% 为 P2 可清理），但「磁盘写满→数据丢失风险」按 F-003 应为 P0 不得自愈，文档缺「磁盘满=P0 升级、禁止清理触碰受保护卷」的升级档；c) Redis 在 F-005 可限重启，但 F-006 又禁数据一致性风险操作，需明确判据。
  - 建议：为每类自愈动作补充「允许/禁止」判定矩阵 + 触发升级的具体判据（连接池重建仅限无在途写、先确认非联动故障；磁盘分层阈值 85%=P2 清理、95%/写满=P0 升级禁止清卷；Redis 重启仅限缓存/会话且确认非持久队列数据源）。

#### Major（强烈建议整改）

- **M1｜自愈误判/抖动/风暴无保护**：健康探针瞬闪或误报可能触发对**健康服务**的多余 restart/回滚，缺「二次独立信号确认」「no-flap/冷却期」「自愈频率上限」。仅 UC-012 异常流提「复核排除」，无统一防抖门禁。建议：自愈前须 ≥2 个独立信号佐证 + 冷却/退避 + 单服务自愈次数/小时上限（超限转升级，防自愈风暴）。
- **M2｜回滚正确性缺口**：UC-004 前置只要求「有上一稳定版本快照」，未要求上一版本**曾经 QA 签收且健康**——否则可能回滚进另一个已坏的版本；也未处理「回滚后配置漂移/依赖不齐」。建议：回滚目标须命中「最近一次 QA 通过」的版本集，回滚后校验配置与依赖一致性。
- **M3｜安全：自愈动作成为攻击面 + 最小权限粒度不足**：若 AI SRE 被攻陷，其可自动 tigger 大量 prod restart/回滚/清理（武器化/放大攻击）。NFR-S 仅笼统「最小权限」，未按动作类映射角色、无可带签名白名单（动作需角色令牌+签名 allowlist 校验）、无干跑/异常上限/紧急熔断开关。建议：自愈动作与凭证分离、动作白名单带显式授权与签名、增加紧急 kill-switch 与每日异常动作上限。
- **M4｜数据一致性判据缺失（Redis「数据损坏」、DB 只读基线）**：UC-011 要 AI SRE「判断是否数据损坏」但 F/NFR 未给判据；NFR-S 说无 prod DB 写权限但未定义「只读连接」作为能力基线。建议：定义只读数据源、判定数据损坏的具体信号、以及「自愈触碰有状态服务」的硬约束。
- **M5｜生产自愈绕过 SVA/发布窗治理**：UC-002/003/004/011 的自动 restart/rollback/清理在 prod 直接生效，未定义与 SVA gate、QA 签收、变更窗/发布冻结/停机窗口（F-007 提了「停机窗口」但无联动机制）的关系。建议：需求层给出「何时自动动作免门禁、何时必须先经 PM 软授权」的治理规则，避免自愈成为灰色地带。
- **M6｜AC/测试覆盖不足**：主 F-005（含重启容器/清理磁盘/回滚/释放资源/重启 Redis 5 类）仅 AC-005（restart）一条，回滚、Redis、磁盘清理均无对应 AC；缺「白名单外动作被拦截」的负向 AC（仅 AC-006 DB 一例）；缺升级链路失败时告警持久化/补发的 AC。建议：按动作类各补 1 AC，并增加负向与失败路径 AC。

#### Minor（可后续完善，不阻塞）

- **m1｜UC↔F 追溯缺失**：12 用例与 8 功能对应不显式呈现（UC-009/010 无唯一归属 F，UC-006 有多个候选），建议加 UC→F 追溯列或矩阵，保证每条功能至少被一条用例+AC 覆盖。
- **m2｜UC-010 角色混淆**：「执行角色 AI SRE + CHECKER」把下游质检消费方写成共同执行者；CHECKER 不执行自愈审计写入。建议：执行=AISRE，CHECKER 角色移入协作接口说明。
- **m3｜NFR-A「旁路不侵入」与自愈动作相抵**：AISRE 监控旁路不侵入主链路成立，但自动 restart/回滚/清理本身即触碰主链路，措辞易误导。建议改为「监控无侵入 + 自愈动作经门禁且可观测」。
- **m4｜监控数据保留 vs 审计取证冲突**：NFR-C 允许清理旧日志/回收，但自愈涉及生产变更，可能需事后取证/审计，缺「正在调查/审计的日志不得清理」保护。
- **m5｜AI SRE 自身可用性兜底薄弱**：UC-009 异常流仅「由 PM 侧兜底」，未定义 PM watchdog 失效后的兜底环。建议补 watchdog 多层或对等健康对账。
- **m6｜升级去重/抑制缺失**：多条 UC 会向 PM/DEVOPS 升级，缺去重、节流、按 P0/P1 收敛通知，存在告警疲劳与重复 Issue 风险。建议补通知去重与聚合策略。
- **m7｜AI SRE 自身平台/代码/配置的维护归属未定义**：谁运维 AI SRE 运行时、谁 review 其代码/自愈配置变更、AISRE 自身出问题回滚由谁负责，均未落位。建议纳入 DEVOPS/PM 职责或在范围外注明由既有角色接管。

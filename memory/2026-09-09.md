## 09-09 决策记录（用户对话）— AI-SRE 产品定位 + #372 定案 ✅

### #372 定案：SQLite 嵌入式（选项 D）
- 结论：incident 持久化用 **SQLite 嵌入式**（单文件），**不用 PG 独立服务**，也不用内存参照。
- 理由：AI-SRE 是可重复部署的产品，须自包含零运维；但它是记忆 agent，单客户 incident 量小，SQLite 够规模，将来可升 PG。
- 关键澄清：GitHub 是「软件开发项目管控」工具，**不是** AI-SRE 运行时存储；「GitHub Issue 唯一真相源」指缺陷桥接到客户 issue 系统，非 incident 存储。

### #370 设计方向清晰（AI-SRE 产品化 + 动态能力配置）
1. **产品定位**：SAS = 两个可重复部署产品（School Admin System + AI-SRE IT operator）。AI-SRE 是「运维同事」不是「被动服务」。
2. **架构分层**：Layer1 执行引擎（已有 ai-sre-service）+ 记录层 SQLite + 记忆层 agent memory + 真相源（客户 issue 系统，可选集成）+ Layer2 沟通层（agent，多通道多租户）。
3. **配置分两层**：
   - 第1层 产品默认 **md playbook**（AI-SRE DNA：专业能力+安全红线+沟通协议，LLM 可读，部署者不改）
   - 第2层 部署者初设 **yaml**（接哪个系统/通道/阈值/路由）
4. **核心诉求：动态可改、零代码变更** — 「怎么当 SRE」放 md（巡检/检测/triage/自愈/汇报/分析/沟通 7 模块），改 md 即强化 AI-SRE，零 build 零重启；安全红线锁代码层不可配置绕过。
5. **6 个交互场景**：晨检报告 / 工单播报 / 运行问答 / 报障 / incident 列表 / 缺陷分析建议。
